# アイコンフレーム メーカー

フレーム画像の**背景透過**と、**アイコン写真への重ね合わせ**を、ひとつづきの3ステップにまとめたブラウザツールです。

TikTok でアイコンフレームを配布したときに寄せられる「これ、どうやって使うんですか？」に、
リンク1本で答えられるようにするためのものです。アプリのインストールも、会員登録も、
画像のアップロードも要りません。

```
① アイコンにする写真をえらぶ  →  ② フレームをえらぶ（背景は自動でとうめい）  →  ③ 位置をあわせて保存
```

同じ端末内処理の考えかたで、**うごく素材（動画）の背景けし**も持っています。
配信に重ねるオーバーレイを作るためのもので、`#/studio` にあります。
詳しくは「[うごく素材の背景けし（スタジオ）](#うごく素材の背景けしスタジオ)」を参照してください。

---

## つかう人にとっての特徴

- **迷うところがない。** 画面には常に「いま押すボタン」が1つだけ大きく出ます。
  細かい調整は「うまく消えないときは」の中にしまってあり、必要な人だけが開きます。
- **背景けしは全自動。** 画像を見て、白などの単色背景か・AIで切り抜くべきか・
  もう透過ずみかを勝手に判断して実行します。ユーザーは何も選びません。
- **直せる。** 自動でうまくいかなかったときのために、色の選び直し、しきい値、
  フチの処理、指でなぞる修正、1つ前に戻る、が全部あります。
- **画像は端末から出ません。** 通信するのは AI モデルの本体を取りにいくときだけで、
  写真そのものはどこにも送信されません。
- **ぜんぶ日本語、むずかしい言葉なし。** 「アルファチャンネル」「マスク」などは使っていません。
- 音・振動は**オンオフできます**（設定は次回も覚えています）。

## ステップ3でできること

「位置をあわせる」画面は、指でも、ボタンでも、キーボードでも同じことができます。
どれか1つしか使えない人（指が思うように動かない、パソコンから使っている、
そもそもピンチ操作を知らない）が行き止まりにならないようにするためです。

| したいこと   | 指              | ボタン・スライダー                 | キーボード                           |
| ------------ | --------------- | ---------------------------------- | ------------------------------------ |
| 動かす       | つまんで動かす  | —                                  | 矢印キー（4px）／Shift＋矢印（20px） |
| 大きさ       | 2本指でひろげる | −／＋ ボタン、「大きさ」スライダー | ＋／− キー、ホイール                 |
| かたむき     | 2本指でまわす   | 「かたむき」スライダー             | —                                    |
| 左右反転     | —               | 反転ボタン                         | —                                    |
| 写真のかたち | —               | そのまま／まる／かどまる／しかく   | —                                    |
| もとに戻す   | —               | 「位置をもどす」                   | —                                    |

- **動かす相手を選べます。**「写真をうごかす／フレームをうごかす」で切り替えます。
  フレーム側も動かせるので、フレームの中心と顔の位置がずれているデザインでも合わせられます。
- **写真のかたち。** 下じきにする写真そのものを、まる／かどまる／しかくに切りぬけます。
  フレームの内側に写真を小さくおさめるとき、四角い角がはみ出さなくなります。
  切りぬきは回転のあとに掛けているので、写真をかたむけると形も一緒にかたむきます。
- **すきまの色。** 写真を小さくすると、まわりが透明のまま残ります。透明の PNG は
  SNS によっては黒や白で塗りつぶされるので、とうめい／白／黒から自分で選べます。
- **まるく切りぬく。** SNS のアイコンは丸く表示されるので、既定で丸く切ります。
  切られる範囲は、暗幕と破線でその場に出しています（保存してから気づくのでは遅いので）。
- 初めて開いたときだけ、プレビューの上に「指でうごかせます」と出します。
  一度でも触ったら、または6秒たったら引っ込めます（ボタンだけで操作する人の視界に
  居座らないため）。

## 携帯にほぞんする

**「保存したのに写真アプリに入ってこない」は、いちばん多いつまずきです。** 原因は2つあり、
どちらもコード側でしか直せません。

1. **`navigator.share` には有効期限があります。** 指が離れてから少しの間しか呼べません。
   ボタンを押してから PNG を作ると 0.2〜1秒かかるので、その間に期限が切れて共有シートが
   開きません。しかも投げられる例外は「利用者が閉じた」ときと見分けがつきにくく、
   **黙って何も起きなかったように見えます。**
   → 画面の中身が変わるたびに、裏で PNG を作っておきます（止まってから 0.5 秒後）。
   押した瞬間には待ち時間ゼロで共有シートを呼べます。
2. **`<a download>` は iOS では「写真」ではなく「ファイル」アプリに入ります。**
   写真アプリに入れる道は、共有シートか、画像の長おし →「写真に追加」しかありません。
   → その両方を出します。

そのうえで、**「携帯に入ってこないときは」を常に出しています。** 押すと、できあがった
画像そのものを大きく出したシートが開きます。ここに置くのは `<canvas>` ではなく `<img>` です
（長おしのメニューが出るのは `<img>` だけなので）。

### いちばん大きいボタンは、端末によって中身が違う

**iPhone と Android で、保存の道が正反対です。**

|         | 共有シート                                               | ダウンロード           |
| ------- | -------------------------------------------------------- | ---------------------- |
| iPhone  | 「画像を保存」がある。**写真アプリに入れる道はここだけ** | 「ファイル」アプリ行き |
| Android | Gmail・Instagram に送るだけ。**保存の項目が無い**        | ここで保存できる       |

なので端末を見て、主役のボタンを入れ替えます。iPhone は共有、それ以外はダウンロード。
もう片方は下に小さく残します。Android の共有ボタンには
**「（保存ではありません）」**と書き添えます —— Instagram に直接送れるのは便利ですが、
保存だと思って押した人が困るので。

同じ理由で、**Android では共有できても「保存しました」と出しません。**
共有できた＝保存できた、ではないからです。

### 枠の中（お試しリンク・埋めこみプレビュー）で開かれたとき

`<iframe sandbox>` の中では、**ダウンロードそのものがブラウザに止められます。**
やっかいなのは `<a download>` が例外を投げないことで、こちらからは成功したように見えます。
実際、お試しリンクで「保存できました」と出たまま1枚も落ちてこない、という報告がありました。

`window.self !== window.top` で枠の中にいることは分かるので、そのときは

- **「保存できました」と言い切らない**
- かわりに長おしできる画像のシートを開く
- 「いま別のサイトの中で開かれています」と、事情のほうを説明する

ようにしています。検証にも、実際にサンドボックスの iframe に入れて確かめる項目があります
（`■ 枠の中で開かれたとき`）。

**お試しリンクは動作確認には使えません。** 保存まわりを試すときは、公開した本物の URL を
開いてください。

## 開発

**引き継ぎ・はじめて触る人は、先に [`docs/HANDOFF.md`](docs/HANDOFF.md) を読んでください。**
触りかた、変えてはいけない約束、実際に踏んだ落とし穴、いまの状態と次の一手が
そこにまとまっています（この README は「何を作ったか・なぜそう作ったか」です）。

```bash
npm install
npm run dev       # 開発サーバー
npm run build     # dist/ に本番ビルド
npm run preview   # ビルド結果の確認
npm test          # 実ブラウザでの検証（先に npm run build が必要）
npm run build:demo  # HTML1枚に全部を埋め込んだ「お試し版」（dist-demo/）
```

`build:demo` は、ファイル1つ配れば動く版を作ります。外部通信ができない場所に
置く前提なので AI 切り抜きは無効で、色キーに落ちます（通信が切れた端末で通る道と同じ）。

Node 22 以上。ビルド成果物は静的ファイルだけなので、どこにでも置けます。

### 検証

`npm test` は実際に Chromium を起動し、画像を読み込ませて、**出力画素のアルファを
読んで**判定します。透過の良し悪しは目で見ないと分からないと思われがちですが、
次のことは機械的に確かめられます。

- 四隅とまん中の穴が透明になっているか
- リング本体・うすい色のベタ塗りが、半透明にならず残っているか
- 囲まれた白（提灯の紙・狐面・泡）に穴が開いていないか
- グローが階調のまま残っているか（半透明画素の割合で測る）
- 暗い写真に重ねたとき、グローが色を保っているか（逆合成が効いているか）
- 透過ずみの画像で、半透明部分の**色が変わっていない**か
- スクショから UI が落ち、フレームが正方形に近く切り出されているか
- 手なおしが、画面を行き来しても消えないか

検証用の画像は `tests/fixtures.mjs` がその場で描き起こします。実際に配布されている
フレームの見た目を似せたものではなく、**透過処理がつまずく性質だけ**を取り出した
ものです（グロー／囲まれた白／白地に白／うすい色／端ぎりぎりの文字／スクショ）。

うごく素材のスタジオも、同じ考えかたで見ています。加えて、ここでは
**書き出したファイルを読み直すところまで**やります。

- 検証用の動画は、ブラウザ自身に録らせます（リポジトリに動画を置かず、
  H.264 の鍵が無い環境でも必ず開けるようにするため）
- 消したあとの舞台の画素（地は透明・前景は残る）
- 見くらべのつまみを動かしたときの、左右の画素
- 緑の地から抜いたとき、フチが緑に光っていないか（いちばん外側の不透明な画素の色を読む）
- 黒い地の光もので、**裾が半透明のまま残っているか**（芯だけになっていないか）
- 光の仕組みそのもの（`tests/mp4.mjs`。地は残らないか、そばの粒は足されるか、
  **遠くの印は足さないか**、四角の外へなだらかに弱まるか、光が無い素材で余計なことをしないか）
- **書き出した透過WebM を開き直して、すみが透明のままか**
- グリーン背景の動画を開き直して、地が緑で塗られているか
- PNG連番が ZIP として開けるか（コマと、読みかたを書いた紙が入っているか）
- 長さが書かれていない WebM でも、コマ数を数えられるか
- **書き出しの途中で画面を離れたとき**、止まるか・止まっているあいだ進まないか・
  戻ったら最後まで録れるか・再開したあとのコマにも透過が残っているか
- いちどに引き受ける量の計算（`tests/mp4.mjs`。予算を超えるコマ数を返さないか、
  コマを半分にすると倍の長さを受けられるか、範囲の収めかたで動かした端が残るか）
- 正しく録れたものに、注意書きを出していないか（確かめが難癖をつけていないか）

**iPhone から使ったとき**は、名乗り（User-Agent）と、分かれ道の入口だけを置き換えて見ています。
端末そのものを再現するのではなく、「どちらへ行くか」を確かめるためです。

- いちばん上の行き先が「できること」になっているか（「できません」から始まっていないか）
- 透明を持てない事情と、緑の外しかたが、その場に書いてあるか
- いちばん大きいボタンが「写真に保存する」（共有シート）になっているか
- 勝手にダウンロードを始めていないか
- 押したときに、テキストではなく**ファイルそのもの**を共有シートへ渡しているか
- つくる画面を開いただけでは、スタジオの中身を落としてこないこと
- MP4 をほどく部分は、中身の分かる MP4 をその場で組み立てて突き合わせます
  （`tests/mp4.mjs`）

### 本物のフレームで確かめる

`tests/real/` というフォルダを作り、自分の作ったフレーム画像（png / jpg / webp）を
放り込んでから `npm test` を実行すると、1枚ずつ通して次を確かめます。

- 外側の背景が抜けているか（四隅）
- まん中の穴が抜けているか（ここが抜けていないと、重ねても写真が見えない）
- 絵が消えていないか／背景が残っていないか（面積比が妥当な範囲か）
- 処理中にエラーが出ていないか

出力には半透明画素の割合も出るので、グローや水彩のにじみが残っているかの目安になります。
`tests/real/` は `.gitignore` 済みです。フレームは作った人のものなので、リポジトリには
入りません。画像を置かなければ、この項目は黙って飛ばされます。

### 公開

既定のブランチに push すると `.github/workflows/deploy.yml` が GitHub Pages に公開します。
はじめの1回だけ、**人が手でやる作業が2つ**あります。

1. **リポジトリを public にする。**
   Settings → General → Danger Zone → Change repository visibility。
   private のままだと Pages に有料プラン（Pro）が要ります。画像はすべて端末の中だけで
   処理するので、公開して困る情報（鍵・個人情報）はコードに入っていません。
2. **Settings → Pages → Source を「GitHub Actions」にする。**
   **ここは自動化できません。** ワークフローに有効化させる設定（`enablement: true`）を
   private のときと public にしたあとの2回試して、どちらも
   `Create Pages site failed. Resource not accessible by integration` で落ちました。
   ワークフローの既定のトークンには Pages サイトを**作る**権限が無いためで、
   公開・非公開とは関係ありません（deploy する権限はあります）。

これを忘れると、ビルドも検証も通るのに `Get Pages site failed` で止まります。

ベースURLは相対パス（`./`）でビルドしているので、`https://ユーザー名.github.io/ae-Frame/`
でも独自ドメインの直下でも、同じ成果物がそのまま動きます。

## 入力はスクリーンショット

TikTok は透過を持てません。フレームは動画・画像として流れるので、受け取る側は
**スクショで持ってくる**のが実際にいちばん多い入力です。そこには必ず余計なものが
写り込みます —— 時刻、ユーザー名、キャプション、右側のボタン列、上下の余白。

そのまま透過すると、フレーム本体はキャンバスの片隅の小さな輪になり、UI の文字や
アイコンが点々と残った、使えない画像になります。そこで読み込んだ直後に、
**フレームらしい部分だけを自動で切り出して**から本処理に渡しています。

どの塊を残すかは、2つの物差しで決めます。

1. **本体の近くにあること。** いちばん大きな塊をフレーム本体とみなし、その近くにある
   ものだけを残します。距離は画像の大きさではなく*本体の大きさ*に対して測ります
   （スクショは画像自体が縦長なので、画像基準だと物差しが伸びすぎる）。
2. **画面のふちに貼りついていないこと。** 時刻もキャプションもボタン列も、
   どれも画面の端に寄っています。一方フレームは真ん中にあって端から離れている。
   この差だけで UI をきれいに落とせます。

切り取りが起きたときは画面にそう表示し、**「切り取らずに全部つかう」で取り消せます**。
面積があまり変わらないときは切り取らないので、ふつうのフレーム画像では何も起きません。

## 背景透過のしくみ

「1つの手法で全部やる」のではなく、**画像を見て手法を選び、3つの層を重ねて**最終的な透明度を作っています。

### 1. 手法は「推測」ではなく「結果」で決める

最初は、縁の色のばらつきを見て「ばらついていたら AI」と決めていました。これは失敗でした。
**ネオンのグローに簡単に騙される**からです。光が画像のふちまで届いていると縁がばらついて
見えるので、色キーできれいに抜けるフレームまで AI に回してしまう。数十MBのダウンロードを
強いたうえ、細い線は AI のほうが鈍ります。

いまはこうしています。

1. すでに透過ずみ（半透明の画素が2%以上）なら、**そのまま通す**
2. それ以外は、まず**色キー**をかける
3. その結果を**検算**し、失敗していたら **AI** に回す

線画のフレームは白い紙の上に描かれていることが多く、その場合は AI より色キーのほうが
輪郭がシャープに出ます。「AIが常に最良」ではありません。

しきい値も自動で決めます。縁の色差の98パーセンタイル＋余裕、という取り方なので、
JPEG のノイズや、うっすらしたグラデーション背景を吸収します。

**検算のしかた。** 失敗は4つの形で現れます。

| 症状               | 見かた                                             |
| ------------------ | -------------------------------------------------- |
| 背景が消えていない | **四隅が不透明**。フレームは丸いので四隅はまず背景 |
| 絵がほとんど消えた | 面積比 0.6% 未満（白いガラスを白地に描いた場合）   |
| 何も消えていない   | 面積比 75% 超                                      |
| 粉々になった       | 断片の数が多すぎる                                 |

断片の数はよく効きます。実測すると、うまく抜けたフレームは **1〜3個**、
ざらざらした背景で失敗したときは **110個** でした。細い線画は面積が小さいので
面積比だけでは失敗と区別できませんが、「細くてもひとつながり」なら断片は1個です。

### 2. 色キーは「白を全部消す」ではない

ここがこのツールの中心です。素の色キー（同じ色の画素を全部消す）は、
アイコンフレームにはそのままでは使えません。

- 提灯の紙、狐面の白、白い泡、ガラスのハイライト —— これらは**デザインの一部**
  なのに背景と同じ白なので、穴が開く
- ネオンのグローや水彩のにじみは**背景色に溶けた階調**なので、ハードに切ると光が死ぬ

そこで、次の3つを組み合わせています。

**(a) つながりで守る。** 背景の塗りつぶしを「画像の四辺」と「画像の中心」の
2か所から流します。中心から流すのは、リング状フレームのまん中の穴を抜くため
（ここが抜けていないと、重ねたときにアイコン写真が隠れます）。中心の種は、
中心付近がほんとうに背景色のときだけ蒔くので、中心まで絵が詰まったデザインは
食い破りません。**どちらからも届かなかった背景色は、デザインの一部として復活**
させます。これで提灯の紙も狐面も残ります。

**(b) 塗りつぶしが通れる不透明度に上限を置く。** ここを高くすると、うすい水色の
リング（アルファ 225 など）を塗りつぶしがすり抜け、内側の泡まで消えてしまいます。
「明らかに背景」と言える画素だけを通し、半分でも残っている絵は壁として扱います。
逆に、復活させるのも「消えかけている画素」だけです。一律に不透明へ戻すと、
せっかく階調で残したネオンの光が、のっぺりした輪に潰れてしまうので。

**(c) 境目の幅は、初期状態ではつねに最小。** ここは避けようのない曖昧さに触れています。
**白い背景の上では、うすい光とうすい絵の具は同じ色になります。** 画素だけを見て
区別する手立てはありません。幅を 0.3 にすると「白との色差が 0.31 未満の色をまとめて
うすくする」ことになり、ネオンの光にはそれが要りますが、花火と淡い水彩が同居する
デザインでは絵のほうまで透けます。

どちらを既定にするかは、**失敗したときの気づきやすさ**で決めました。消え残りは画面を
見ればすぐ分かり、スライダーでも筆でも直せます。一方、絵がうっすら透けたのは
気づきにくく、書き出したあとでは直せません。だから既定は「消しすぎない」側に倒し、
光を階調で残したい人が「光のにじみを残す」を上げる、という順番にしています。

代償として、ネオンのフレームは既定のままだと光が「階調」ではなく「色」として残ります
（暗い写真に重ねたときの、外へ消えていくフェードは出ません）。スライダーを上げれば戻ります。
境目のギザギザは別に用意したぼかし（feather）が均すので、ここを広げる必要はありません。

なお「デザインの中の白もけす」をオンにすると、(a) を切って素の色キーに戻せます。

### すでに透過ずみの画像には、何もしない

いちばん壊しやすい入力です。アルファはもう正しく付いているので、**色にもアルファにも
さわってはいけません**。とくに背景色の引き算（下記の逆合成）をかけると、付いていない
白を引くことになり、半透明のグローの色が沈みます（水色が緑に寄って暗くなる）。
そのため、この経路では引き算の初期値を 0 にしています。他のツールで作られた
「白フチが焼き付いた透過PNG」もあるので、スライダーで足せる余地は残してあります。

**AI切り抜き** — [transformers.js](https://github.com/huggingface/transformers.js) で
マッティングモデルをブラウザ内で実行します（`src/lib/ai.ts`）。

- モデルは **RMBG-1.4 → BiRefNet-lite → MODNet** の順に試し、1つ落ちても次に進みます
- WebGPU が使えれば WebGPU、なければ WASM。精度に応じて `fp16` / `q8` / `fp32` を選択
- ロジットを返すモデルにはシグモイドを、値域が偏る出力にはコントラスト補正を自動でかけます
- マスクは canvas ではなくバイリニアで拡大しています（境界がなめらかになるため）
- モデルはブラウザにキャッシュされるので、2回目からはダウンロードなしで動きます
- 読み込みに失敗しても**行き止まりにしません**。色キーに自動で切り替え、日本語で理由を出します

AI に回ったときも、ユーザーには「AIできれいにしています」としか見えません。
判断は上の検算が勝手にやります。

### 3. 仕上げと手描き

最終的な透明度は、次の3層の重ね合わせです。

1. **ベース透明度** — 上の手法が出した結果
2. **仕上げ** — フチ削り（最小値フィルタ）、ぼかし（分離型ボックスぼかし×2）、
   そして**フチの色抜き**
3. **手描きマスク** — 「消しのこりを消す」「消えすぎをもどす」の筆

**フチの色抜き**は地味ですが、いちばん効きます。半透明の画素は
`観測色 = α × 本来の色 + (1 - α) × 背景色` になっているので、これを本来の色について解いて
背景色の混入を引き算します（逆合成）。

効果は「白いフチが消える」だけではありません。ネオンのグローや水彩のにじみが
**「うすい水色」ではなく「本来の色を薄く重ねたもの」**になるので、暗いアイコン写真の上に
重ねても色がくすまず、ちゃんと発光して見えます。ただし α が小さいほど割り算で誤差が
暴れるので、ごく薄いところでは効きを弱めています。

3層を別々に持っているので、**しきい値を動かしても手描きの修正は消えません**し、
手法を切り替えてもやり直しになりません。

## うごく素材の背景けし（スタジオ）

`#/studio` にある、**動画と画像の背景を消すための画面**です。
つくる画面（アイコンフレーム）とは道具が別なので、URL も、見た目も、分けてあります。

想定しているのは、TikTok の配信に重ねる素材づくりです。
生成AIで作った動画や、手元で撮った動画から、被写体だけを抜いて、
OBS や TikTok LIVE Studio、CapCut にそのまま渡せる形にします。

```
① 動画や画像を置く  →  ② 背景をけす（AIが1コマずつ）  →  ③ 使う場所をえらんで書き出す
```

### 出口は4つ。形式名ではなく「行き先」で選ばせる

WebM・MP4・PNG連番・アルファチャンネル。どれも、**使う人が知りたい言葉ではありません。**
知りたいのは「OBS に置けるのはどれか」「CapCut で使えるのはどれか」だけです。
だから保存の画面では、見出しを行き先の名前にして、形式はその下に小さく置いています。

| 行き先                         | 出るもの              | なぜその形か                                           |
| ------------------------------ | --------------------- | ------------------------------------------------------ |
| 配信ソフト（OBS・LIVE Studio） | 透過WebM（VP8/VP9）   | 透明のまま置ける。手数がいちばん少ない                 |
| CapCut などの編集アプリ        | 緑背景つき MP4/WebM   | スマホの編集アプリは透過動画を読めないことが多い       |
| パソコンの編集ソフト           | 透過PNG連番（ZIP）    | 画質が落ちない。1秒あたりのコマ数を書いた紙も同梱する  |
| そのまま投稿                   | 背景を敷いた MP4/WebM | 画面で選んでいる背景（色・ぼかし・画像）のまま書き出す |

### 透過のまま動画にできる道は、ひとつしかない

**MP4（H.264）は透明を持てません。** 持てるのは WebM（VP8/VP9）と Apple の HEVC with alpha で、
ブラウザから作れるのは前者だけです。そのうえ WebCodecs の `VideoEncoder` は
`alpha: 'keep'` を受け付けません（2026年8月時点、どの実装も未対応。
`isConfigSupported` に聞くと `supported: false` が返ります）。

残るのは `MediaRecorder` で、**canvas の透明はそのまま VP8/VP9 に入ります。**
検証では、書き出したファイルを読み直して、すみの不透明度が 0 のままであることまで確かめています
（`■ うごく素材のスタジオ` の「渡した先でも、背景が無いまま」）。

そのかわり MediaRecorder は**実時間でしか録れません**。10秒の素材は10秒かかります。
速さではなく、透過が保たれることを取りました。急ぐ人・画質を優先する人のために、
実時間の縛りが無い **PNG連番** を並べてあります。

### コマの取り出しかたを2つ持っている

| 方法                   | 使うとき                       | 長所                             | 短所                       |
| ---------------------- | ------------------------------ | -------------------------------- | -------------------------- |
| WebCodecs              | H.264 の MP4 で、鍵がある端末  | 速い。コマの取りこぼし・重複なし | MP4 を自分でほどく必要あり |
| `<video>` を進めて描く | WebM、ほどけない MP4、古い端末 | どこでも動く                     | seek 1回ごとに数十ミリ秒   |

WebCodecs は「コンテナをほどく」機能を持っていないので、MP4 をほどく部分
（`src/lib/video/mp4.ts`）は自分で書いています。ライブラリを足すこともできましたが、
必要なのは _映像トラックを1本みつける / avcC を取り出す / コマの位置・大きさ・時刻・
キーフレームを並べる_ の3つだけで、それは1ファイルに収まります。

ほどけない形（分割された MP4・H.264 以外・そもそも MP4 でない）のときは `null` を返し、
呼ぶ側が黙って `<video>` の道に落ちます。**「解けなかった」は失敗ではなく、ふつうに起こること**
として扱っています。

なお、ほどいた結果が正しいかどうかは画面を見ても分かりません（ずれていても絵は出ます）。
検証用の Chromium には H.264 の鍵も入っていません。そこで検証では、
**中身の分かっている MP4 をその場で組み立てて**、位置・大きさ・時刻・キーフレームを
1つずつ突き合わせています（`tests/mp4.mjs`）。

### 持っているのは「マット」だけ

10秒・24コマ/秒の動画は 240 枚あります。仕上がりの絵をそのまま全部持つと
1280×720×4バイト×240 で **880MB** になり、スマホでは即座に落ちます。

そこで持つのは濃さ1枚ぶん（1バイト）だけ、しかも小さめの解像度にしています。
512×288 なら1コマ 147KB、240コマで **35MB**。元の絵は、見せるときも書き出すときも
`<video>` から取り直し、マットは拡大して重ねます（拡大でフチはむしろなめらかになります）。

この作りには、もう1つ効きます。**フチを削る・ぼかす・フチの色を抜くを「あとから」かけられる**
ことです。AI の結果を書き換えるのではなく、見せる直前・書き出す直前にかけているので、
つまみを動かした瞬間に絵が変わります。240コマの再計算は起きません。

### ちらつきを止める

AI は1コマずつ独立に見るので、止まっているはずのフチがコマごとに 1〜2px 揺れます。
静止画では気づきませんが、動かすと輪郭がチリチリ震えて見えます
（「AI切り抜きっぽさ」の正体はこれです）。

前のコマと**大きく変わったところ**（本当に動いた場所）はそのまま通し、
わずかしか変わっていないところだけ前の値に寄せます。動きを鈍らせずに、震えだけが止まります。

### フチの色を抜く

つまみは1つですが、中では2つのことをしています。

**(1) 半透明の画素から、背景の色を引く**

半透明の画素は「前景 × a ＋ 背景 ×(1−a)」で出来ています。背景の色が分かっているなら、
その分を引けば前景の色が戻ります。

```
前景 =（見えている色 − 背景 ×(1−a)）÷ a
```

背景の色は、消えた側（マットがほぼ 0）の画素の平均から推定します。
これをやらないと、暗い場所で撮った素材は輪郭に黒いふちが残り、
**白い画面に置いたときだけ**「切り抜きました」という顔になります。

**(2) 不透明な画素に乗った「色かぶり」を抑える**

グリーンバックでは (1) だけでは足りませんでした。緑の地は光を反射するので、
**被写体のフチそのものが緑に染まります。** そこは半透明ではなく不透明なので、
(1) は手を出しません。動画の圧縮（色情報を間引く方式）が、さらに緑をにじませます。

結果、切り抜きの縁だけが緑に光ります。検証用の緑素材で、画面を見ていて気づきました。

放送の現場で使われている考えかたは単純で、**「緑が、赤と青の平均を超えている分だけ削る」**。
緑の服や緑のぬいぐるみは赤と青も一緒に持っているので、生き残ります。

この (2) は、**地が緑や青のときだけ**働きます。暗いスタジオ撮りのような無彩色の地では、
削るべき色かぶりがありません。そこで働かせると、ただ色を濁らせるだけになります。

**(3) クロマキーのときは、境目の幅も広げる**

(2) を入れてもまだ緑が残りました。もとの見立ては「白い地のイラスト」向けで、
境目を狭く取るようにできています（絵を余計に削らないため）。

グリーンバックの動画は事情が違います。緑の照り返しに加えて、**動画の圧縮が色情報を
間引く**（4:2:0）ので、緑と被写体が混ざった帯が数画素ぶん残ります。境目を狭く取ると
その帯が「完全に不透明」と判定され、縁が緑に光ります。

そこで、地がクロマキーだと分かったときだけ境目を広げます。広げること自体が目的ではなく、
帯を半透明として拾って **(1) の引き算が効く状態にする**のが目的です。
この3つが揃って、はじめて緑が落ちました（検証では、いちばん外側の不透明な画素の色を読んで
見張っています）。

### 黒い地の「光もの」

生成AIで作った素材や、火花・きらめき・ネオンの素材は、**黒い地でしか作れません。**
白い地に置くと光が見えないからです。作る側としては当然の選択なのですが、
そのあと切り抜こうとすると行き詰まります。

- **AI は「被写体はどれか」を見ます。** 宙に浮いた粒子や、にじんだ光は被写体として
  扱われないので、まるごと消えます
- **色キーは「この色を消す」です。** 黒を消すと、光の裾（暗い側）も一緒に消えます。
  残るのは芯だけになり、ふわっとした感じが死にます

**光の正体は「足し算」です。** 黒い地に写っている光は、地の色に足された分そのもの。
だから明るさをそのまま透明度にして、色を割り戻せば、どんな地の上でも「足し算」と
同じ見えかたになります。

```
透明度 a = 明るさ
色     c = 見えている色 ÷ a     ← 割り戻し（「フチの色をとる」が受け持つ）
```

ただし**これだけでは足りません。** 実際の素材（黒ホリで撮ったぬいぐるみ）で試すと、
粒子と口の中の光は完璧に残ったのに、**体の暗いところが透けてスカスカになりました。**
明るさを透明度にする方法は、光には合っていても、塊には合っていません。

そこで、片方だけにしません。

```
最終的な濃さ ＝ max( 塊のマット（AI か 色キー）, 光のマット（明るさ） )
```

塊は塊のまま、まわりの光は光のまま残ります。**気づくのも自動です**——1コマ目を見て
「消えた側に、明るいものが残っていないか」を数え、残っていれば光を足します。
外したときは「光を残す」を 0 にすれば元どおりです。

光を拾う範囲は、**被写体を囲む四角を少し広げたところまで**に限っています。
「明るいものを残す」は画面のどこにでも効いてしまうので、実際の素材で試したときに
**右下に入っている生成AIの印まで残りました。** 光は被写体のまわりに出るものなので、
そう決めています（四角の縁で急に切ると線が出るので、外へなだらかに弱めます）。

光だけの素材（火花・きらめき・ネオンだけが写っているもの）には、
消しかたの「光だけ」を用意しています。

**なお、配信ソフトで使うなら、透過にしないほうが上です。**
OBS はソースごとにブレンドモードを持っている（右クリック →
ブレンドモード → スクリーン／加算）ので、**黒い地のまま置いて画面を切り替えるだけで、
劣化なしに光が乗ります。** 保存の画面でも、光ものだと分かったときはそう書き添えます。

### 待たせかたを設計する

AI は1コマ 60〜300ミリ秒かかります。240コマなら 20秒〜2分。
待たせること自体は避けられないので、待ちかたのほうを作りました。

- **進捗はバーではなくフィルム。** バーは「あとどれくらいか」しか言えません。
  フィルムなら、それに加えて**どんな仕上がりかを、待っているあいだに見せられます。**
  うまくいっていないこと（体が欠けている等）に30秒待ってから気づくのと、
  5コマ目で気づくのとでは、やり直しの重さが違います。
- **長い動画は、はじめの15秒だけを選んだ状態で渡します。** フィルムの両はしを動かせば変えられます。
- **「なめらかさ 半分」** を用意しています。コマ数が半分になるぶん、待ち時間も半分です。
- 背景が単色（グリーンバック・白ホリ）だと気づいたときは、AI を通しません。
  色で消せば1コマ2〜3ミリ秒で、240コマでも1秒かかりません。**判断は自動で、結果だけ一言出します。**

### 途中で画面を離れられたとき

書き出しは実時間で進みます。10秒の素材なら10秒かかり、そのあいだ人は待ちます。
待つあいだに、別のタブを見にいきます。通知に応えます。画面が消えます。
**それはふつうの行動であって、失敗ではありません。**

ところがブラウザは、見えていない画面のコマ送りを止めます
（`requestVideoFrameCallback` も `requestAnimationFrame` も呼ばれなくなる）。
いっぽう `<video>` は再生を続け、録音機も時間を刻み続けます。結果できあがるのは、
**途中から止め絵になった動画**でした。しかも本人は最後まで録れたと思っているので、
気づくのは配信の最中になります。

なので、見えなくなったら本当に止めます。

- `<video>` を止める（時間が進まない）
- 録音機も止める（`pause()` は時間の刻みごと止まるので、継ぎ目が残らない）
- 戻ってきたら両方を起こし、コマ送りを繋ぎ直す
- 止めていることは画面に出す（進捗が動かない理由が分からないと、壊れたと判断されます）

再開のときは**世代番号**を進めています。止める前に入れたコマ送りの予約は取り消せず、
戻った瞬間に古い予約と新しい予約の2本が走って、1コマを二重に録ってしまうためです。

消している最中・書き出している最中にタブを閉じようとしたときは、いちど引きとめます。
作りかけはどこにも残らない（端末の中だけで処理している）ので、閉じれば全部消えます。

### いちどに引き受ける量

マットは全部メモリに持ちます。上限を置かないと、3分の動画で 5400 コマ・1.2GB になり、
**数分待たせたあとに、何も残さずタブごと消えます。**

そこで、受けられる長さを先に計算して、渡される前に縮めています（`lib/video/budget.ts`）。

| 素材                 | 1コマのマット | 受けられるコマ数 | 30コマ/秒なら | 半分（15コマ/秒）なら |
| -------------------- | ------------- | ---------------- | ------------- | --------------------- |
| 1280×720 / 4K / 縦長 | 225KB         | 約 728           | 約 24秒       | 約 48秒               |

マットは長辺 640 に揃えて持つので、**4K でも 720p でも 1コマの重さは同じ**です。
つまり上限は解像度ではなく、1秒あたりのコマ数だけで決まります。

フィルムの端は、上限のところで止まります（断るのではなく、伸ばせるところまで伸びて
止まるので、触っているうちに分かります）。「なめらかさ」を半分にすると上限は倍になり、
その案内もその場に出ます。処理の側にも同じ上限を置いてあります——画面の側の制限は
親切であって保証ではないので、最後の砦は数えて止める側に持たせています。

### iPhone から使うとき

端末ごとに正反対のことが起きる場所なので、一次情報にあたって確かめました。

- **Safari が録れるのは MP4（H.264 / AAC）だけ**です（MediaRecorder の対応形式）。
  MP4 は透明を持てないので、**iPhone・iPad では透過の動画そのものが作れません。**
- **写真アプリに入れる道は共有シートだけ**です。ダウンロードは「ファイル」アプリ行きになります。
- WebKit には「canvas の captureStream から録ると中身が空の動画になる」という報告が残っています
  （[bugs.webkit.org 229611](https://bugs.webkit.org/show_bug.cgi?id=229611)）。

そこでこうしています。

- **行き先そのものを差し替える。** 透過で録れない端末では「配信ソフトに、そのまま置く」を消して、
  代わりに「配信ソフト・編集アプリで使う（緑の背景つき）」を主役に出します。
  そこに**なぜ緑なのか**を書いてあります。
  はじめは「透過の動画は作れません」という札を別に置いていましたが、並べてみると
  iPhone で保存を開いたとき**最初に目に入るのが「できません」**になったのでやめました。
  できることを先に置いて、事情はその中で説明します。
- **保存のボタンを入れ替える。** iPhone では「写真に保存する」（共有シート）を主役に、
  ダウンロードは「（ファイルアプリ）」と書き添えて下に置きます。
- **iPhone では、書き出しのあとに自分からダウンロードを始めません。**
  始めても「ファイル」止まりで、しかも何が起きたのか分からないまま画面が切り替わります。
  共有シートは指が離れてすぐでないと開けないので、押してもらう形にしています。
- 判定は**端末の名前ではなく、実際に録れるかどうか**でしています。
  バージョンで分けると、対応が増えた日にこちらだけが古いままになります。

### 出来上がりを、渡す前に開いて確かめる

「録れる形式か」は `MediaRecorder` に聞けば答えます。けれど**答えたとおりに録れているか**は
別の話で、中身が空のまま返ってくる環境があります（上の WebKit の報告）。

このツールは「配信で使える素材ができました」と言って渡します。渡した先が本番の配信で、
そこで初めて空だと分かるのは、いちばん悪い順番です。だから渡す前に、
**書き出したファイルを自分で開いて、絵が入っているかを見ます**（`lib/video/export.ts` の `inspect`）。

- マットの「残っている画素の割合」を当てにして、出来上がりと見くらべます
- 透過なら「不透明な画素がほとんど無い」、背景つきなら「明るさの幅がゼロ（＝1色に塗りつぶし）」を疑います
- **見つけてもファイルは取り上げません。** 確かめ自体が外すこともある（この端末で開けないだけ、
  ということもありうる）ので、渡したうえで、注意書きを添えるだけにしています

検証には「正しく録れたものに注意書きを出さない」という項目も入れてあります。
良い出来のものに毎回「怪しい」と出たら、注意書きそのものが読まれなくなるためです。

### 画面のつくり

- 上から **舞台 → 背景チップ → フィルム → 主ボタン → こまかい調整（畳んである）**。
  「置く・けす・使う」の順そのままです。
- どの瞬間でも、**色が付いた大きなボタンは1つだけ**。迷いは選択肢の数ではなく
  「どれが今なのか分からないこと」から生まれます。
- **舞台の外は徹底して暗く、無彩色にしてあります。** 透明を確かめる作業は
  まわりの明るさに引っぱられるためです（白い画面では白フチが見えません）。
  有彩色を出すのは「いま押すところ」と「意味を持つ色そのもの」（緑・市松）だけです。
- **舞台の上には効果をかけません。** ビネットも粒子も乗せません。
  映っているものは、保存されるものと1ピクセルも違ってはいけません。
- 市松もようは CSS の背景で、**canvas の中には描いていません。**
  描いてしまうと「見えている絵」と「保存される絵」が別物になります。
- 見くらべ（before / after）は並べずに重ね、境目を指で動かします。並べると両方が小さくなります。

### スタジオについて分かっている制限

- **iPhone / iPad では、透過の動画は作れません。** Safari が録れるのは MP4 だけで、
  MP4 は透明を持てないためです。この端末では行き先そのものを差し替え、
  「緑の背景つき」を主役に出します（上の「iPhone から使うとき」）。
  透明のまま渡したいときは PNG連番を使ってください。
- **書き出しは実時間です。** 10秒の素材の書き出しには10秒かかります（PNG連番を除く）。
  そのあいだに別の画面へ移ると、**いったん止まって、戻ると続きから録ります**
  （止まっていることは画面に出ます）。待ち時間はそのぶん延びます。
- **PNG連番は重いです。** 720p・10秒で 100MB を超えることがあります。
  開いたときに1コマだけ実際に書き出して測り、押す前に見当を出しています。
- **スマホでの AI 切り抜きは遅いです。** WebGPU の無い端末では1コマ 0.5〜1.5秒かかります。
  「なめらかさ 半分」と、短く切ることをすすめる文言を出しています。
- **光を残すと、明るいものは何でも残ります。** 被写体のまわりに限ってはいますが、
  そこに写り込んだ明るいもの（画面のすみの印など）が四角の中に入っていれば残ります。
  「光を残す」を下げるか、0 にしてください。
- 音は、書き出す動画にそのまま入ります（PNG連番には入りません）。
  書き出しのあいだ、音はスピーカーには出しません（保存を押したら急に音が出た、を避けるため）。

## 触感のあるUX

音声ファイルは1つも持たず、すべて Web Audio API で合成しています（`src/lib/sound.ts`）。
ねらいは「音楽」ではなく「物を触った感触」なので、どの音も

- 20〜120ms と極端に短い
- アタックが1〜3ms（カチッと立ち上がる）
- 帯域を絞ったノイズの「カチ」＋短いピッチ落ちのトーン

という骨格でできています。あわせて Vibration API を叩くので、対応端末では指にも返ります。

視覚もこれに合わせてあります。影はぼかさず実線のオフセット影にして、押したときに
**影の分だけ本当に沈む**ようにしてあります（`transform: translate(3px, 3px)` と
`box-shadow: 0` の同時変化）。音・振動・見た目の3つが同じタイミングで動くと、
画面の中のものに厚みが出ます。

`prefers-reduced-motion` を設定している人には、アニメーションを止めます。

### 実装上の判断メモ

- **ステップ2と3の画面は、進んでも「隠すだけ」で外しません。** 取り外すと手描きの修正や
  合わせた位置が消えて、戻ってきたときにやり直しになるためです。
- 筆を動かしている間は毎フレーム合成が走るので、`composite()` に使い回しバッファを
  渡せるようにしてあります（1600px 角なら1枚10MB。毎フレーム確保すると引っかかります）。
- フチ削りとぼかしは重いので、合成とは分けて設定変更時にだけ計算します（`finishAlpha`）。
- 「取り消し」は全面のコピーを積まず、筆が触った矩形だけを切り出して積んでいます。
- **スタジオは、開いたときにだけ取りにいきます**（`Root.tsx` の遅延読み込み）。
  静的に読むと、動画を触らない人にも動画まわりのコードと CSS が最初から降ってきます。
  検証にも「つくる画面では、スタジオの中身を落としてこない」という項目があります。
- 市松もようはテーマに追随させていません。ダークテーマで暗い市松にすると、黒い線画の
  フレームが背景に溶けて「消えたのか残ったのか」が分からなくなるためです。
  白いフレーム用に、下じきの色は切り替えられます。
- **プレビューの描画予約は1つだけ持ち、中身は毎回 ref から読みます。**
  予約の中に描画関数を閉じこめると、1フレームに2回状態が変わったとき（＝素早く
  ドラッグしたとき）に予約が取り消されたまま印だけ残り、**以後その画面が永久に
  描き直されなくなる**という事故が起きました。詳細は下の「見つかった不具合」。

## 決済は持たない

**このツールに支払いの導線は1本もありません。** 全機能が無料で、有料機能も
サブスクも、寄付や支援の募集もありません。画面は「つくる」と「知らせる」の2つだけです。

```
つくる（#/） → 保存 → 知らせる（#/share） → またつくる
```

以前は応援（チップ）の受け皿がありました。Stripe の審査を受けて 2026-08 に
丸ごと外しています。**経緯と、戻すときに満たす必要がある条件は
[docs/stripe-compliance.md](docs/stripe-compliance.md) にまとめてあります。**

短く書くと、引っかかったのは「これから作るもののためにお金を集める」と
読める言いかたでした。Stripe がチップに求めるのは
「すでに提供したものへの任意の支払い」であることで、
**将来の成果物に触れた瞬間、それは資金調達になります。**

戻すときは、禁止語の一覧を消して通すのではなく、一覧に当たらない文章を書きます。
そして、その前に Stripe へ確認を取ります。

### 画面の切りかえ

ハッシュ（`#/share`）でやっています。GitHub Pages には「どのURLでも index.html を
返す」設定が無いので、ふつうのパスで直リンクを配ると 404 になるためです。
ルーティングのライブラリは入れていません（画面は2つしかないので）。

配ってしまった古いURL（`#/support` / `#/support/thanks` / `?thanks=1`）は、
知らせるページへ送ったうえで**URL も置き換えます**。置き換えないと、
「戻る」で古いURLへ戻り、また送り返されて、戻れないループになります。

つくる画面は、知らせるページへ寄り道しても**外さずに隠しておきます**。写真も
フレームも、手でなおした跡も、ここで消えると「寄り道したせいで作りかけが消えた」
ことになるので。

## 分かっている制限

- **AI切り抜きの実地確認ができていません。** 開発環境が huggingface.co を遮断しているため、
  モデルの取得から推論までを通しで動かせていません。読み込みに失敗したときに色キーへ
  落ちる経路は確認済みなので行き止まりにはなりませんが、AI 経路そのものは公開後に
  一度確かめてください。**うごく素材のスタジオも同じです**（こちらは色で消す道を
  通しで検証してあり、AI と色は同じ入れ物にマットを入れるので、消しかた以外の
  すべて——コマの取り出し、ゆれ止め、仕上げ、書き出し——は検証の対象に入っています）。
- **iPhone では振動しません。** iOS Safari は Vibration API を持っていません。
  対応端末かどうかを見て、非対応なら振動のスイッチ自体を出さないようにしています
  （iPhone では音と見た目だけで手ざわりを作っています）。
- **HEIC はブラウザ次第です。** iOS の写真アプリから選ぶと多くの場合 JPEG に変換されますが、
  HEIC のまま渡されてデコードできない環境では、日本語で「保存しなおしてください」と出します。
- **AIモデルのライセンス。** 既定の1番手 RMBG-1.4 は非商用の条件付きです。
  フォロワーさんに無料で配る用途なら問題になりませんが、商用にするなら
  `src/lib/ai.ts` の `MODELS` の順番を入れ替えて、MIT の BiRefNet を先頭にしてください。

## 動作環境

Chrome / Edge / Safari / Firefox の最近のバージョン。iOS Safari と Android Chrome で
使う前提のレイアウトです（ホーム画面に追加すればアプリのように開けます）。

AI切り抜きは WebGPU があれば速く、なければ WASM で動きます。
色キーでの透過は**完全にオフラインで**動作します。

うごく素材のスタジオは、上に加えて次を使います。どれも無い場合は、
その機能のカードやボタンを**そもそも出しません**（押せないものを見せない）。

| 使うもの                     | 何に要るか                       | 無いとき                               |
| ---------------------------- | -------------------------------- | -------------------------------------- |
| WebCodecs（VideoDecoder）    | MP4 からの速いコマ取り出し       | `<video>` を進める道に落ちる           |
| MediaRecorder（VP8/VP9）     | 透過WebM の書き出し              | 透過WebM のカードを出さない（iOS）     |
| MediaRecorder（MP4 か WebM） | グリーン背景・背景つきの書き出し | そのカードを出さない                   |
| `requestVideoFrameCallback`  | コマ落ちしない書き出し           | `requestAnimationFrame` で代わりに回す |
