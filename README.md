# アイコンフレーム メーカー

フレーム画像の**背景透過**と、**アイコン写真への重ね合わせ**を、ひとつづきの3ステップにまとめたブラウザツールです。

TikTok でアイコンフレームを配布したときに寄せられる「これ、どうやって使うんですか？」に、
リンク1本で答えられるようにするためのものです。アプリのインストールも、会員登録も、
画像のアップロードも要りません。

```
① アイコンにする写真をえらぶ  →  ② フレームをえらぶ（背景は自動でとうめい）  →  ③ 位置をあわせて保存
```

---

## つかう人にとっての特徴

- **迷うところがない。** 画面には常に「いま押すボタン」が1つだけ大きく出ます。
  細かい調整は「うまく消えないときは」の中にしまってあり、必要な人だけが開きます。
- **背景けしは全自動。** 画像を見て、白などの単色背景か・AIで切り抜くべきか・
  もう透過ずみかを勝手に判断して実行します。ユーザーは何も選びません。
- **直せる。** 自動でうまくいかなかったときのために、色の選び直し、しきい値、
  フチの処理、指でなぞる修正、1つ前に戻る、が全部あります。
- **画像は端末から出ません。** 通信するのは AI モデルの本体を取りにいくときだけで、
  写真そのものはどこにも送信されません。
- **ぜんぶ日本語、むずかしい言葉なし。** 「アルファチャンネル」「マスク」などは使っていません。
- 音・振動は**オンオフできます**（設定は次回も覚えています）。

## ステップ3でできること

「位置をあわせる」画面は、指でも、ボタンでも、キーボードでも同じことができます。
どれか1つしか使えない人（指が思うように動かない、パソコンから使っている、
そもそもピンチ操作を知らない）が行き止まりにならないようにするためです。

| したいこと   | 指              | ボタン・スライダー                 | キーボード                           |
| ------------ | --------------- | ---------------------------------- | ------------------------------------ |
| 動かす       | つまんで動かす  | —                                  | 矢印キー（4px）／Shift＋矢印（20px） |
| 大きさ       | 2本指でひろげる | −／＋ ボタン、「大きさ」スライダー | ＋／− キー、ホイール                 |
| かたむき     | 2本指でまわす   | 「かたむき」スライダー             | —                                    |
| 左右反転     | —               | 反転ボタン                         | —                                    |
| 写真のかたち | —               | そのまま／まる／かどまる／しかく   | —                                    |
| もとに戻す   | —               | 「位置をもどす」                   | —                                    |

- **動かす相手を選べます。**「写真をうごかす／フレームをうごかす」で切り替えます。
  フレーム側も動かせるので、フレームの中心と顔の位置がずれているデザインでも合わせられます。
- **写真のかたち。** 下じきにする写真そのものを、まる／かどまる／しかくに切りぬけます。
  フレームの内側に写真を小さくおさめるとき、四角い角がはみ出さなくなります。
  切りぬきは回転のあとに掛けているので、写真をかたむけると形も一緒にかたむきます。
- **すきまの色。** 写真を小さくすると、まわりが透明のまま残ります。透明の PNG は
  SNS によっては黒や白で塗りつぶされるので、とうめい／白／黒から自分で選べます。
- **まるく切りぬく。** SNS のアイコンは丸く表示されるので、既定で丸く切ります。
  切られる範囲は、暗幕と破線でその場に出しています（保存してから気づくのでは遅いので）。
- 初めて開いたときだけ、プレビューの上に「指でうごかせます」と出します。
  一度でも触ったら、または6秒たったら引っ込めます（ボタンだけで操作する人の視界に
  居座らないため）。

## 携帯にほぞんする

**「保存したのに写真アプリに入ってこない」は、いちばん多いつまずきです。** 原因は2つあり、
どちらもコード側でしか直せません。

1. **`navigator.share` には有効期限があります。** 指が離れてから少しの間しか呼べません。
   ボタンを押してから PNG を作ると 0.2〜1秒かかるので、その間に期限が切れて共有シートが
   開きません。しかも投げられる例外は「利用者が閉じた」ときと見分けがつきにくく、
   **黙って何も起きなかったように見えます。**
   → 画面の中身が変わるたびに、裏で PNG を作っておきます（止まってから 0.5 秒後）。
   押した瞬間には待ち時間ゼロで共有シートを呼べます。
2. **`<a download>` は iOS では「写真」ではなく「ファイル」アプリに入ります。**
   写真アプリに入れる道は、共有シートか、画像の長おし →「写真に追加」しかありません。
   → その両方を出します。

そのうえで、**「携帯に入ってこないときは」を常に出しています。** 押すと、できあがった
画像そのものを大きく出したシートが開きます。ここに置くのは `<canvas>` ではなく `<img>` です
（長おしのメニューが出るのは `<img>` だけなので）。

### いちばん大きいボタンは、端末によって中身が違う

**iPhone と Android で、保存の道が正反対です。**

|         | 共有シート                                               | ダウンロード           |
| ------- | -------------------------------------------------------- | ---------------------- |
| iPhone  | 「画像を保存」がある。**写真アプリに入れる道はここだけ** | 「ファイル」アプリ行き |
| Android | Gmail・Instagram に送るだけ。**保存の項目が無い**        | ここで保存できる       |

なので端末を見て、主役のボタンを入れ替えます。iPhone は共有、それ以外はダウンロード。
もう片方は下に小さく残します。Android の共有ボタンには
**「（保存ではありません）」**と書き添えます —— Instagram に直接送れるのは便利ですが、
保存だと思って押した人が困るので。

同じ理由で、**Android では共有できても「保存しました」と出しません。**
共有できた＝保存できた、ではないからです。

### 枠の中（お試しリンク・埋めこみプレビュー）で開かれたとき

`<iframe sandbox>` の中では、**ダウンロードそのものがブラウザに止められます。**
やっかいなのは `<a download>` が例外を投げないことで、こちらからは成功したように見えます。
実際、お試しリンクで「保存できました」と出たまま1枚も落ちてこない、という報告がありました。

`window.self !== window.top` で枠の中にいることは分かるので、そのときは

- **「保存できました」と言い切らない**
- かわりに長おしできる画像のシートを開く
- 「いま別のサイトの中で開かれています」と、事情のほうを説明する

ようにしています。検証にも、実際にサンドボックスの iframe に入れて確かめる項目があります
（`■ 枠の中で開かれたとき`）。

**お試しリンクは動作確認には使えません。** 保存まわりを試すときは、公開した本物の URL を
開いてください。

## 開発

```bash
npm install
npm run dev       # 開発サーバー
npm run build     # dist/ に本番ビルド
npm run preview   # ビルド結果の確認
npm test          # 実ブラウザでの検証（先に npm run build が必要）
npm run build:demo  # HTML1枚に全部を埋め込んだ「お試し版」（dist-demo/）
```

`build:demo` は、ファイル1つ配れば動く版を作ります。外部通信ができない場所に
置く前提なので AI 切り抜きは無効で、色キーに落ちます（通信が切れた端末で通る道と同じ）。

Node 22 以上。ビルド成果物は静的ファイルだけなので、どこにでも置けます。

### 検証

`npm test` は実際に Chromium を起動し、画像を読み込ませて、**出力画素のアルファを
読んで**判定します。透過の良し悪しは目で見ないと分からないと思われがちですが、
次のことは機械的に確かめられます。

- 四隅とまん中の穴が透明になっているか
- リング本体・うすい色のベタ塗りが、半透明にならず残っているか
- 囲まれた白（提灯の紙・狐面・泡）に穴が開いていないか
- グローが階調のまま残っているか（半透明画素の割合で測る）
- 暗い写真に重ねたとき、グローが色を保っているか（逆合成が効いているか）
- 透過ずみの画像で、半透明部分の**色が変わっていない**か
- スクショから UI が落ち、フレームが正方形に近く切り出されているか
- 手なおしが、画面を行き来しても消えないか

検証用の画像は `tests/fixtures.mjs` がその場で描き起こします。実際に配布されている
フレームの見た目を似せたものではなく、**透過処理がつまずく性質だけ**を取り出した
ものです（グロー／囲まれた白／白地に白／うすい色／端ぎりぎりの文字／スクショ）。

### 本物のフレームで確かめる

`tests/real/` というフォルダを作り、自分の作ったフレーム画像（png / jpg / webp）を
放り込んでから `npm test` を実行すると、1枚ずつ通して次を確かめます。

- 外側の背景が抜けているか（四隅）
- まん中の穴が抜けているか（ここが抜けていないと、重ねても写真が見えない）
- 絵が消えていないか／背景が残っていないか（面積比が妥当な範囲か）
- 処理中にエラーが出ていないか

出力には半透明画素の割合も出るので、グローや水彩のにじみが残っているかの目安になります。
`tests/real/` は `.gitignore` 済みです。フレームは作った人のものなので、リポジトリには
入りません。画像を置かなければ、この項目は黙って飛ばされます。

### 公開

既定のブランチに push すると `.github/workflows/deploy.yml` が GitHub Pages に公開します。
はじめの1回だけ、**人が手でやる作業が2つ**あります。

1. **リポジトリを public にする。**
   Settings → General → Danger Zone → Change repository visibility。
   private のままだと Pages に有料プラン（Pro）が要ります。画像はすべて端末の中だけで
   処理するので、公開して困る情報（鍵・個人情報）はコードに入っていません。
2. **Settings → Pages → Source を「GitHub Actions」にする。**
   **ここは自動化できません。** ワークフローに有効化させる設定（`enablement: true`）を
   private のときと public にしたあとの2回試して、どちらも
   `Create Pages site failed. Resource not accessible by integration` で落ちました。
   ワークフローの既定のトークンには Pages サイトを**作る**権限が無いためで、
   公開・非公開とは関係ありません（deploy する権限はあります）。

これを忘れると、ビルドも検証も通るのに `Get Pages site failed` で止まります。

ベースURLは相対パス（`./`）でビルドしているので、`https://ユーザー名.github.io/ae-Frame/`
でも独自ドメインの直下でも、同じ成果物がそのまま動きます。

## 入力はスクリーンショット

TikTok は透過を持てません。フレームは動画・画像として流れるので、受け取る側は
**スクショで持ってくる**のが実際にいちばん多い入力です。そこには必ず余計なものが
写り込みます —— 時刻、ユーザー名、キャプション、右側のボタン列、上下の余白。

そのまま透過すると、フレーム本体はキャンバスの片隅の小さな輪になり、UI の文字や
アイコンが点々と残った、使えない画像になります。そこで読み込んだ直後に、
**フレームらしい部分だけを自動で切り出して**から本処理に渡しています。

どの塊を残すかは、2つの物差しで決めます。

1. **本体の近くにあること。** いちばん大きな塊をフレーム本体とみなし、その近くにある
   ものだけを残します。距離は画像の大きさではなく*本体の大きさ*に対して測ります
   （スクショは画像自体が縦長なので、画像基準だと物差しが伸びすぎる）。
2. **画面のふちに貼りついていないこと。** 時刻もキャプションもボタン列も、
   どれも画面の端に寄っています。一方フレームは真ん中にあって端から離れている。
   この差だけで UI をきれいに落とせます。

切り取りが起きたときは画面にそう表示し、**「切り取らずに全部つかう」で取り消せます**。
面積があまり変わらないときは切り取らないので、ふつうのフレーム画像では何も起きません。

## 背景透過のしくみ

「1つの手法で全部やる」のではなく、**画像を見て手法を選び、3つの層を重ねて**最終的な透明度を作っています。

### 1. 手法は「推測」ではなく「結果」で決める

最初は、縁の色のばらつきを見て「ばらついていたら AI」と決めていました。これは失敗でした。
**ネオンのグローに簡単に騙される**からです。光が画像のふちまで届いていると縁がばらついて
見えるので、色キーできれいに抜けるフレームまで AI に回してしまう。数十MBのダウンロードを
強いたうえ、細い線は AI のほうが鈍ります。

いまはこうしています。

1. すでに透過ずみ（半透明の画素が2%以上）なら、**そのまま通す**
2. それ以外は、まず**色キー**をかける
3. その結果を**検算**し、失敗していたら **AI** に回す

線画のフレームは白い紙の上に描かれていることが多く、その場合は AI より色キーのほうが
輪郭がシャープに出ます。「AIが常に最良」ではありません。

しきい値も自動で決めます。縁の色差の98パーセンタイル＋余裕、という取り方なので、
JPEG のノイズや、うっすらしたグラデーション背景を吸収します。

**検算のしかた。** 失敗は4つの形で現れます。

| 症状               | 見かた                                             |
| ------------------ | -------------------------------------------------- |
| 背景が消えていない | **四隅が不透明**。フレームは丸いので四隅はまず背景 |
| 絵がほとんど消えた | 面積比 0.6% 未満（白いガラスを白地に描いた場合）   |
| 何も消えていない   | 面積比 75% 超                                      |
| 粉々になった       | 断片の数が多すぎる                                 |

断片の数はよく効きます。実測すると、うまく抜けたフレームは **1〜3個**、
ざらざらした背景で失敗したときは **110個** でした。細い線画は面積が小さいので
面積比だけでは失敗と区別できませんが、「細くてもひとつながり」なら断片は1個です。

### 2. 色キーは「白を全部消す」ではない

ここがこのツールの中心です。素の色キー（同じ色の画素を全部消す）は、
アイコンフレームにはそのままでは使えません。

- 提灯の紙、狐面の白、白い泡、ガラスのハイライト —— これらは**デザインの一部**
  なのに背景と同じ白なので、穴が開く
- ネオンのグローや水彩のにじみは**背景色に溶けた階調**なので、ハードに切ると光が死ぬ

そこで、次の3つを組み合わせています。

**(a) つながりで守る。** 背景の塗りつぶしを「画像の四辺」と「画像の中心」の
2か所から流します。中心から流すのは、リング状フレームのまん中の穴を抜くため
（ここが抜けていないと、重ねたときにアイコン写真が隠れます）。中心の種は、
中心付近がほんとうに背景色のときだけ蒔くので、中心まで絵が詰まったデザインは
食い破りません。**どちらからも届かなかった背景色は、デザインの一部として復活**
させます。これで提灯の紙も狐面も残ります。

**(b) 塗りつぶしが通れる不透明度に上限を置く。** ここを高くすると、うすい水色の
リング（アルファ 225 など）を塗りつぶしがすり抜け、内側の泡まで消えてしまいます。
「明らかに背景」と言える画素だけを通し、半分でも残っている絵は壁として扱います。
逆に、復活させるのも「消えかけている画素」だけです。一律に不透明へ戻すと、
せっかく階調で残したネオンの光が、のっぺりした輪に潰れてしまうので。

**(c) 境目の幅は、初期状態ではつねに最小。** ここは避けようのない曖昧さに触れています。
**白い背景の上では、うすい光とうすい絵の具は同じ色になります。** 画素だけを見て
区別する手立てはありません。幅を 0.3 にすると「白との色差が 0.31 未満の色をまとめて
うすくする」ことになり、ネオンの光にはそれが要りますが、花火と淡い水彩が同居する
デザインでは絵のほうまで透けます。

どちらを既定にするかは、**失敗したときの気づきやすさ**で決めました。消え残りは画面を
見ればすぐ分かり、スライダーでも筆でも直せます。一方、絵がうっすら透けたのは
気づきにくく、書き出したあとでは直せません。だから既定は「消しすぎない」側に倒し、
光を階調で残したい人が「光のにじみを残す」を上げる、という順番にしています。

代償として、ネオンのフレームは既定のままだと光が「階調」ではなく「色」として残ります
（暗い写真に重ねたときの、外へ消えていくフェードは出ません）。スライダーを上げれば戻ります。
境目のギザギザは別に用意したぼかし（feather）が均すので、ここを広げる必要はありません。

なお「デザインの中の白もけす」をオンにすると、(a) を切って素の色キーに戻せます。

### すでに透過ずみの画像には、何もしない

いちばん壊しやすい入力です。アルファはもう正しく付いているので、**色にもアルファにも
さわってはいけません**。とくに背景色の引き算（下記の逆合成）をかけると、付いていない
白を引くことになり、半透明のグローの色が沈みます（水色が緑に寄って暗くなる）。
そのため、この経路では引き算の初期値を 0 にしています。他のツールで作られた
「白フチが焼き付いた透過PNG」もあるので、スライダーで足せる余地は残してあります。

**AI切り抜き** — [transformers.js](https://github.com/huggingface/transformers.js) で
マッティングモデルをブラウザ内で実行します（`src/lib/ai.ts`）。

- モデルは **RMBG-1.4 → BiRefNet-lite → MODNet** の順に試し、1つ落ちても次に進みます
- WebGPU が使えれば WebGPU、なければ WASM。精度に応じて `fp16` / `q8` / `fp32` を選択
- ロジットを返すモデルにはシグモイドを、値域が偏る出力にはコントラスト補正を自動でかけます
- マスクは canvas ではなくバイリニアで拡大しています（境界がなめらかになるため）
- モデルはブラウザにキャッシュされるので、2回目からはダウンロードなしで動きます
- 読み込みに失敗しても**行き止まりにしません**。色キーに自動で切り替え、日本語で理由を出します

AI に回ったときも、ユーザーには「AIできれいにしています」としか見えません。
判断は上の検算が勝手にやります。

### 3. 仕上げと手描き

最終的な透明度は、次の3層の重ね合わせです。

1. **ベース透明度** — 上の手法が出した結果
2. **仕上げ** — フチ削り（最小値フィルタ）、ぼかし（分離型ボックスぼかし×2）、
   そして**フチの色抜き**
3. **手描きマスク** — 「消しのこりを消す」「消えすぎをもどす」の筆

**フチの色抜き**は地味ですが、いちばん効きます。半透明の画素は
`観測色 = α × 本来の色 + (1 - α) × 背景色` になっているので、これを本来の色について解いて
背景色の混入を引き算します（逆合成）。

効果は「白いフチが消える」だけではありません。ネオンのグローや水彩のにじみが
**「うすい水色」ではなく「本来の色を薄く重ねたもの」**になるので、暗いアイコン写真の上に
重ねても色がくすまず、ちゃんと発光して見えます。ただし α が小さいほど割り算で誤差が
暴れるので、ごく薄いところでは効きを弱めています。

3層を別々に持っているので、**しきい値を動かしても手描きの修正は消えません**し、
手法を切り替えてもやり直しになりません。

## 触感のあるUX

音声ファイルは1つも持たず、すべて Web Audio API で合成しています（`src/lib/sound.ts`）。
ねらいは「音楽」ではなく「物を触った感触」なので、どの音も

- 20〜120ms と極端に短い
- アタックが1〜3ms（カチッと立ち上がる）
- 帯域を絞ったノイズの「カチ」＋短いピッチ落ちのトーン

という骨格でできています。あわせて Vibration API を叩くので、対応端末では指にも返ります。

視覚もこれに合わせてあります。影はぼかさず実線のオフセット影にして、押したときに
**影の分だけ本当に沈む**ようにしてあります（`transform: translate(3px, 3px)` と
`box-shadow: 0` の同時変化）。音・振動・見た目の3つが同じタイミングで動くと、
画面の中のものに厚みが出ます。

`prefers-reduced-motion` を設定している人には、アニメーションを止めます。

### 実装上の判断メモ

- **ステップ2と3の画面は、進んでも「隠すだけ」で外しません。** 取り外すと手描きの修正や
  合わせた位置が消えて、戻ってきたときにやり直しになるためです。
- 筆を動かしている間は毎フレーム合成が走るので、`composite()` に使い回しバッファを
  渡せるようにしてあります（1600px 角なら1枚10MB。毎フレーム確保すると引っかかります）。
- フチ削りとぼかしは重いので、合成とは分けて設定変更時にだけ計算します（`finishAlpha`）。
- 「取り消し」は全面のコピーを積まず、筆が触った矩形だけを切り出して積んでいます。
- 市松もようはテーマに追随させていません。ダークテーマで暗い市松にすると、黒い線画の
  フレームが背景に溶けて「消えたのか残ったのか」が分からなくなるためです。
  白いフレーム用に、下じきの色は切り替えられます。
- **プレビューの描画予約は1つだけ持ち、中身は毎回 ref から読みます。**
  予約の中に描画関数を閉じこめると、1フレームに2回状態が変わったとき（＝素早く
  ドラッグしたとき）に予約が取り消されたまま印だけ残り、**以後その画面が永久に
  描き直されなくなる**という事故が起きました。詳細は下の「見つかった不具合」。

## 決済は持たない

**このツールに支払いの導線は1本もありません。** 全機能が無料で、有料機能も
サブスクも、寄付や支援の募集もありません。画面は「つくる」と「知らせる」の2つだけです。

```
つくる（#/） → 保存 → 知らせる（#/share） → またつくる
```

以前は応援（チップ）の受け皿がありました。Stripe の審査を受けて 2026-08 に
丸ごと外しています。**経緯と、戻すときに満たす必要がある条件は
[docs/stripe-compliance.md](docs/stripe-compliance.md) にまとめてあります。**

短く書くと、引っかかったのは「これから作るもののためにお金を集める」と
読める言いかたでした。Stripe がチップに求めるのは
「すでに提供したものへの任意の支払い」であることで、
**将来の成果物に触れた瞬間、それは資金調達になります。**

戻すときは、禁止語の一覧を消して通すのではなく、一覧に当たらない文章を書きます。
そして、その前に Stripe へ確認を取ります。

### 画面の切りかえ

ハッシュ（`#/share`）でやっています。GitHub Pages には「どのURLでも index.html を
返す」設定が無いので、ふつうのパスで直リンクを配ると 404 になるためです。
ルーティングのライブラリは入れていません（画面は2つしかないので）。

配ってしまった古いURL（`#/support` / `#/support/thanks` / `?thanks=1`）は、
知らせるページへ送ったうえで**URL も置き換えます**。置き換えないと、
「戻る」で古いURLへ戻り、また送り返されて、戻れないループになります。

つくる画面は、知らせるページへ寄り道しても**外さずに隠しておきます**。写真も
フレームも、手でなおした跡も、ここで消えると「寄り道したせいで作りかけが消えた」
ことになるので。

### 点検

```
npm run check:dist
```

配るもの（`dist/`）とリポジトリの両方を直接読んで、資金集めに読める文言・
決済リンク・秘密鍵・前のビルドの残りかすが無いことを確かめます。`npm test` にも含まれます。

**画面ではなくファイルを読む**のが要点です。一度、条件分岐の向こうに置いて
「画面に出さない」ところで止めてしまい、文字列は配られる JS に残ったままでした。
画面を見る検証では、この壊れかたは永久に捕まえられません。

## 分かっている制限

- **AI切り抜きの実地確認ができていません。** 開発環境が huggingface.co を遮断しているため、
  モデルの取得から推論までを通しで動かせていません。読み込みに失敗したときに色キーへ
  落ちる経路は確認済みなので行き止まりにはなりませんが、AI 経路そのものは公開後に
  一度確かめてください。
- **iPhone では振動しません。** iOS Safari は Vibration API を持っていません。
  対応端末かどうかを見て、非対応なら振動のスイッチ自体を出さないようにしています
  （iPhone では音と見た目だけで手ざわりを作っています）。
- **HEIC はブラウザ次第です。** iOS の写真アプリから選ぶと多くの場合 JPEG に変換されますが、
  HEIC のまま渡されてデコードできない環境では、日本語で「保存しなおしてください」と出します。
- **AIモデルのライセンス。** 既定の1番手 RMBG-1.4 は非商用の条件付きです。
  フォロワーさんに無料で配る用途なら問題になりませんが、商用にするなら
  `src/lib/ai.ts` の `MODELS` の順番を入れ替えて、MIT の BiRefNet を先頭にしてください。
