アイコンフレーム メーカー

フレーム画像の背景透過と、アイコン写真への重ね合わせを、3ステップにまとめたブラウザツール。 この資料は「どう動いているか」より先に「なぜそう決めたか」を残すために書いています。

まず

これは何のためのものか

TikTok でアイコンフレームを配布すると必ず来る「これ、どうやって使うんですか？」に、 リンク1本で答えられるようにするためのツールです。 アプリのインストールも、会員登録も、画像のアップロードもありません。 処理はすべて見ている人の端末の中で完結します。

使う人はスマホしか持っていない前提で作ってあります。 画面に出ている「いま押すボタン」は常に1つだけ。細かい調整は折りたたみの中にしまってあり、 うまくいかなかった人だけが開きます。専門用語（アルファチャンネル、マスク等）は使っていません。

触って確かめる： お試し版（HTML1枚に全部入り）。スマホでそのまま最後まで動きます。AI切り抜きだけは、この置き場所が外部通信できないため無効です。

いまどこ

現在の状況（2026-08-11）

公開ずみで、決済の輪はひととおり通っています。 実機（Android・本番URL）で つくる → 保存 → 応援 → Stripe（テストモード） → お礼 → もう1個つくる を最後まで確認しました。テスト決済のあと ?thanks=1 で戻ってきて、お礼のページが出るところまで通っています。

できていること

  • GitHub Pages で公開（リポジトリは public、Pages の Source は GitHub Actions）
  • 3ステップ（写真 → 背景けし → 重ねて保存）が実機で通る
  • 保存が iPhone / Android / パソコンの3経路すべてで成立する
  • 応援ページ（#/support）とお礼ページ（#/support/thanks）
  • Stripe 支払いリンク4本を接続（URL は src/tip-config.ts にだけ書いてある）
  • 決済から戻る道を4通り（session_id 付き・末尾スラッシュ・大文字・?thanks=1）受けられる
  • 実ブラウザでの通し検証 144項目、CI で毎回全通し

つくる側のハリネズミ ——「飾り」ではなく「場面」

この道具の画面には、これまで絵を一切置いてきませんでした。 そこへハリネズミを入れるにあたって、線を1本引いてあります。 ずっと出ているものは1つも作らない。 何かが起きた瞬間だけ出て、用が済むと消えます。

いつ出るか絵消えるとき
まだ写真を選んでいない寝ている子写真を選んだ瞬間
AI の読み込みを待っているコーヒーの子切り抜きが終わったとき
保存できた手を振る子やり直したとき
つかいかたを開いた歩いている子シートを閉じたとき

ステップ2（背景をけす）には置いていません。 あそこは、とうめいになったかどうかを目で判定する画面です。 横に色のついた絵があると判断が鈍ります。市松の下じきをテーマに 追随させなかったのと同じ理由で、ここは譲れません。

場面が来るまで要素そのものが存在しないので、その瞬間まで 取りに行きません。1枚 23〜36KB。つくるページが 0.28MB → 0.34MB になったのは、 最初に開いたときだけ2匹（空っぽの枠とつかいかたシート）が出るためで、 写真を選ぶと以後は出ません。

「出っぱなしになっていないか」は検証で見張っています （写真をえらぶ前は1匹だけ／選んだら消える／背景をけす画面には出さない）。 絵を足すとこの線はなし崩しになりやすいので、機械に見てもらう形にしました。

飾りの置きかた（方針）

「BLUE FRUIT LAB の世界観をサイト全面へ敷く」のではなく、 「静かで機能的な ae-Frame の余白へ、研究標本の気配だけを薄く置く」。

守るもの：生成り〜白の地／薄いグリッド／細い黒線／赤い操作アクセント／大きな余白／操作性優先。 避けるもの：全画面装飾、UIより装飾が目立つ状態、 サイバーUI化、ネオン広告化、キラキラ過多、背景画像の大量追加。

画面置いたもの
つくる 装飾なし。方眼（body::before / opacity 0.035）だけ。 ここは透過の結果を目で確かめる画面なので、背景に色があると判断の邪魔になる
応援 地（opacity 0.18）＋ 左上に葡萄 ＋ 右下に水。3枚まで
お礼 地は画像を使わない。CSS の radial-gradient 2本（0KB） ＋ 右下に水 ＋ カードを縁取る水の輪

実画面に置いてから直したことが2つあります。 地の濃さを 0.5 から 0.18 へ（0.5 ではパソコンの画面がまるごと 水色の紙になり、生成りとグリッドという地の本体が消えていました）。 葡萄をお礼ページから外した（短い文とボタン1つを読ませる場所に、 角の飾りをもう1枚足すと読ませたいものの周りが埋まる。−250KB）。

一度外して、置きかたを直して戻した素材：水の輪（support-celebration）

最初は「この素材は使えない」と判断しました。それは間違いでした。 使えなかったのは絵ではなく、こちらの置きかたです。

絵は中央がまるく空いた輪で、何かを囲むために描かれています。 それを画面いっぱい（background-size: cover）に引き伸ばしていたので、 輪の左右の腕がパソコンの広い余白に散らばり、水の塊が並んでいるように見えていました。 「UIより目立つ」「広告っぽい」と判定したのは、その状態のことです。

やったこと何が起きたか
1 画面いっぱい（cover / opacity 0.34） 輪の腕が余白に散らばる。不採用と判断
2 本文の列に合わせる（top 0） 腕は収まったが、輪の濃いところがステップ表示に重なり「完了」が泡に埋まる
3 開始をカードの上端へ（top 132px / 幅 +130px） ステップ表示は読めるようになったが、輪の中央がカードに隠れ、左右に水の塊が2つ浮いて見えた
4 広げて薄くする（幅 +300px / opacity 0.46 → 0.34） カードを囲む輪として成立。採用

素材の良し悪しと、置きかたの良し悪しは別のものです。 1つの置きかたで悪く見えたことを、素材そのものの判定にしてしまっていました。 次に「この素材は使えない」と思ったときは、置きかたを2〜3通り試してから決めること。

いまの決まりごとは3つです。画面幅に連動させない （連動させると広い画面ほど輪が余白へ散らばる）。 ステップ表示より下から始める （top: 132px ＝ カードの上端。パソコンで145px、スマホで141px なので1つの値で足ります）。 大きさと濃さは、片方だけ上げる （両方上げるとただの広告になる。いまは広いぶん薄い＝ +300px / 0.34）。 前の2つは検証で見張っています。

見た目の良し悪しは測れませんが、そうなる手前の条件は測れます。 検証に足しました：画面を覆う画像の層は薄い地の1枚まで（opacity 0.25以下）／ 端の飾りは画面の面積の2割まで／お礼ページは地の画像を取りに行かない／ 水の輪の大きさが画面の広さで変わらない／ 水の輪がステップ表示にかからない／ 動きを減らす設定の人には飾りを動かさない／ 開いただけで400KBを超えるものを落とさない。 地の opacity を 0.5 に戻すと、これは実際に落ちます（確認ずみ）。 輪の2件は、実際に踏んだ失敗をそのまま条件にしてあります。

手順

公開する

コードは claude/tiktok-icon-frame-editor-dbgywf ブランチにあります。まだ公開されていません。

  1. ブランチはそのままでよい

    このリポジトリには main がまだ無く、既定のブランチは claude/tiktok-icon-frame-editor-dbgywf のほうです。 公開のワークフローは両方を見るようにしてあるので、 いま push すればそのまま公開されます。 あとから main を作っても、そのまま動きます。

  2. リポジトリを public にする

    Settings → General → いちばん下の Danger Zone → Change repository visibility。 private のままだと GitHub Pages に有料プラン（Pro）が要ります。 このツールは画像をすべて端末の中だけで処理するので、 公開して困る情報（鍵・個人情報）はコードに入っていません。

  3. Settings → Pages → Source を「GitHub Actions」にする

    ここだけは、人が手でやる必要があります。自動化できません。 ワークフローに有効化させる設定（enablement: true）を、 private のときと public にしたあとの2回ためして、どちらも Create Pages site failed. Resource not accessible by integration で落ちました。ワークフローの既定のトークンには Pages サイトを「作る」権限が 無いためで、公開・非公開とは関係ありません（deploy する権限はあります）。 これを忘れると、ビルドも検証も通るのに Get Pages site failed で止まります。

  4. main に push する

    .github/workflows/deploy.yml が型チェック・ビルド・実ブラウザ検証まで通してから公開します。 検証が落ちると公開されません（透過が壊れたまま世に出ないようにするため）。

ベースURLは相対パス（./）でビルドしているので、 https://ユーザー名.github.io/ae-Frame/ でも独自ドメインの直下でも、同じ成果物がそのまま動きます。

核心

背景透過の考えかた

手法は「推測」ではなく「結果」で決める

最初は、画像の縁の色のばらつきを見て「ばらついていたら AI」と決めていました。これは失敗でした。 ネオンのグローに騙されるからです。光が画像のふちまで届いていると縁がばらついて見えるので、 色キーできれいに抜けるフレームまで AI に回してしまう。 数十MBのダウンロードを強いたうえに、細い線は AI のほうが鈍ります。

いまは、こうしています。

  • すでに透過ずみ（半透明の画素が2%以上）なら、何もしない
  • それ以外は、まず色キーをかける
  • その結果を検算し、失敗していたら AI に回す

色キーは「白を全部消す」ではない

ここがこのツールの中心です。素の色キー（同じ色の画素を全部消す）は、アイコンフレームには使えません。 提灯の紙、狐面の白、白い泡、ガラスのハイライトはデザインの一部なのに背景と同じ白だからです。 ネオンのグローや水彩のにじみは背景色に溶けた階調なので、ハードに切ると光が死にます。

そこで3つを組み合わせています。

  • つながりで守る。 背景の塗りつぶしを「画像の四辺」と「画像の中心」の2か所から流し、 どちらからも届かなかった背景色はデザインの一部として復活させます。 中心から流すのはリング状フレームのまん中の穴を抜くため。中心が本当に背景色のときだけ種を蒔くので、 中心まで絵が詰まったデザインは壊しません。
  • 塗りつぶしが通れる濃さに上限を置く。 ここが緩いと、うすい水色のリングを塗りつぶしがすり抜けて内側の泡まで消えます。 復活させるのも「消えかけた画素」だけ。一律に不透明へ戻すと、階調で残したグローが輪に潰れます。
  • 境目の幅をデザインに合わせる。 グローは距離が連続的に変わるので中間の階調が広く散らばり、うすい色のベタ塗りは一点に固まります。 この差をヒストグラムの形で見分けます。

透過ずみの画像には、何もしない

いちばん壊しやすい入力です。アルファはもう正しく付いているので、色にもアルファにも触ってはいけません。 とくに背景色の引き算をかけると、付いていない白を引くことになり、 半透明のグローの色が沈みます。この経路では引き算の初期値を 0 にしています。

フチの色を抜く（逆合成）

半透明の画素は 観測色 = α × 本来の色 + (1 − α) × 背景色 になっています。 これを本来の色について解いて、背景色の混入を引き算します。

効果は「白いフチが消える」だけではありません。グローやにじみが 「うすい水色」ではなく「本来の色を薄く重ねたもの」になるので、 暗いアイコン写真の上に重ねても色がくすまず、ちゃんと発光して見えます。 ただし α が小さいほど割り算で誤差が暴れるので、ごく薄いところでは効きを弱めています。

記録

実機で壊れたもの

作っている途中で実際に踏んだ不具合です。同じ場所をまた壊さないために、症状・原因・証拠を残します。 すべて検証に固定してあるので、再発すれば npm test が落ちます。

CASE 1 提灯の紙と狐面の白に穴が開く
原因 素の色キーが「同じ色の画素を全部消す」ため。デザインの一部としての白も背景と同じ白だった。
対処 外側にも中心の穴にもつながっていない背景色を、デザインの一部として復活させる（つながりで守る）。
CASE 2 うすい水色のリングの内側で、白い泡が消える
原因 うすい色のリングは不透明度が 225 ほどにしかならず、背景の塗りつぶしがそこを すり抜けて内側に入り込んでいた。
対処 塗りつぶしが通れる不透明度の上限を 250 から 128 に。半分でも残っている絵は壁として扱う。
CASE 3 透過ずみPNGの半透明部分の色が沈む
原因 アルファがすでに正しく付いている画像にまで、背景色の引き算をかけていた。付いていない白を引いていた。
対処 この経路では引き算の初期値を 0 に。白フチが焼き付いた画像のために、足す余地は残した。
グローの色  修正前 rgb(0, 212, 212)  →  修正後 rgb(33, 226, 226)　（元 34, 226, 226）
CASE 4 うすい色のフレームが、初期状態でごっそり消える
原因 しきい値を「縁のばらつき＋固定の余裕 0.035」で決めていた。この余裕が、デザインの薄い色そのものと 同じ大きさだった。金魚フレームの水しぶきは白との色差が 0.056 しかなく、 初期値 0.06 にちょうど飲み込まれていた。
原因2 さらにグロー判定の感度が高すぎ、輪郭のアンチエイリアスだけでグローと誤判定して境目を 0.3 まで広げていた。これも薄い色を半透明にしていた。
対処 画像全体のヒストグラムから、背景の山が終わる位置を読んでしきい値にする。境目の幅も 「背景の終わり」から「絵の色が始まる位置」までの隙間に収める。グロー判定は1階級あたりの下限を上げた。
色差 0.02 の輪  修正前 alpha=20  →  修正後 alpha=255（4本すべて）
CASE 5 うすい水しぶきや泡が、枠の外に出て見切れる
原因 切り出しの範囲を「濃い部分（不透明度128超）」だけで測っていたので、薄い部分が範囲外になっていた。
対処 落とすと決めた UI の矩形を避けながら、かすかにでも残っている画素（不透明度8超）まで範囲を広げ直す。
CASE 6 グロー付きフレームが、無駄に AI へ回る
原因 縁の色のばらつきで手法を先に決めていた。光が画像のふちまで届くと縁がばらついて見えるため、 色キーで足りるフレームまで AI 行きになっていた。
対処 常に色キーから始め、結果を検算して駄目なら AI に回す。断片数の上限も 350 → 60 に。
断片数  成功したフレーム 1〜3 個  ／  失敗したもの 110 個
CASE 7 スクショを入れると、フレームが片隅の小さな輪になる
原因 TikTok は透過を持てないので、受け取る側はスクショで持ってくる。時刻・キャプション・ボタン列まで 一緒に入るため、余白を詰める処理がそれらを含めてしまっていた。
対処 読み込んだ直後にフレームだけを切り出す。切り取ったことは画面に出し、取り消せるようにした。
縦横比  修正前 0.46（縦長のまま）  →  修正後 1.00
CASE 8 設定を変えると「くわしい設定」が閉じて、手なおしも消える
原因 処理中に操作パネルごと画面から外していたため、開いていた状態も編集内容も失われていた。
対処 ステップ2と3の画面は、進んでも「隠すだけ」で外さない。手描きの修正も合わせた位置も残る。
CASE 9 「光のにじみを残す」が、効いていないのに大きい値だった
原因 境目の幅を「背景の終わり」から「絵の色が始まる位置」までの隙間から計算していた。 実測すると、線画・祭・金魚・スクショのどれもが上限の 0.2 に張り付いていた。 その範囲には画素が1つも無いので何も起きていないが、たまたまその範囲に色があるデザインが来ると、 理由もなく半透明にしてしまう。
対処 グローがあるときだけ 0.3、それ以外は最小の 0.01 に固定した。境目のギザギザは 「フチのギザギザをとる」（feather）が均す。
副作用 幅を狭くしたことで、提灯の紙のような "背景色にごく近い色" が、アルファ 0 ではなく 184 で止まるようになった。囲まれた部分を戻す条件が 128 未満だったため、紙がうっすら透けた。 階調のないデザインでは完全な不透明まで戻すよう変更（階調があるときは従来どおり控えめ）。
初期値  線画・祭・金魚・スクショ 20  →  1 ／ ネオンは 30 のまま
CASE 10 グローのあるデザインで、絵そのものが透けてしまう
原因 グローを見つけたときだけ境目の幅を 0.3 に広げていた。これは 「白との色差が 0.31 未満の色を、まとめてうすくする」という意味になる。 花火と淡い水彩が同居するようなデザインでは、光だけでなく絵の淡い色まで巻き込まれる。
背景 これは実装の誤りではなく、避けようのない曖昧さに触れている。 白い背景の上では、うすい光とうすい絵の具は同じ色になる。 画素だけを見て区別する手立ては無い。
対処 どちらを既定にするかを、失敗したときの気づきやすさで決めた。消え残りは画面を見ればすぐ分かり、 スライダーでも筆でも直せる。絵がうっすら透けたのは気づきにくく、書き出したあとでは直せない。 そこで初期値はつねに 0.01（＝消しすぎない側）にし、光を階調で残したい人が 「光のにじみを残す」を上げる、という順番にした。
代償 ネオンのフレームは、既定のままだと光が「階調」ではなく「色」として残る。 暗いアイコン写真に重ねたとき、外側へ消えていくフェードは出ない。 スライダーを上げれば戻る（検証で固定してある）。
ネオンの半透明画素  既定 2.3%  ／  にじみを 30 に上げると 12.0%
CASE 11 素早くドラッグしたあと、ステップ3の画面が一切動かなくなる
症状 写真をさっと動かしたあと、大きさスライダーも、左右反転も、矢印キーも、すきまの色も、 見た目が何ひとつ変わらなくなる。値そのものは変わっているので、 画面を行き来して描き直させると、その時点の状態でちゃんと描かれる。
原因 描画は「次のフレームでまとめて1回」に予約していた。予約中かどうかは rafRef に入れた ID で見ていて、片づけのときに cancelAnimationFrame は呼ぶが ID を 0 に戻していなかった。 1フレームの間に状態が2回変わると（＝指が速いと必ず起きる）、 予約は取り消され、しかし「予約中」の印だけが残る。以後 if (rafRef.current) return に引っかかりつづけ、 この画面は二度と描き直されない。
対処 予約は1つだけ持ち、その中身は毎回いちばん新しい描画関数を paintRef から読みにいく形にした。予約の片づけは部品が消えるときだけ。 こうすると、まとめられたフレームでも必ず最新の状態が描かれる（＝コマは落ちても 結果は落ちない）。
見つけかた 人の目には見つけにくい種類の不具合だった。触ると値は動き、画面を離れて戻れば直る。 気づけたのは、検証がドラッグの直後にスライダーを動かしていたから。 ただし当初の検証は 1000 画素に1つの間引きサンプルで比べていて、 「変わっていない」を「たまたま同じ」と読み違えていた。 画面を 12×12 に割って全画素を1回ずつ読む形に変えたら、 ずれが ぴったり 0.00 と出た。ここで初めて、 テストの粗さではなくアプリが止まっていると分かった。
ドラッグ後のずれ  修正前 0.00（凍結）  ／  修正後 33.38（スライダー180%）
CASE 12 保存したのに、写真アプリに入ってこない
原因1 navigator.share には有効期限がある。指が離れてから 少しの間しか呼べない。ボタンを押してから PNG を作ると 0.2〜1秒かかるので、 その間に期限が切れて共有シートが開かない。しかも投げられる例外は 「利用者がシートを閉じた」ときと見分けがつきにくく、こちらは catch で黙って捨てていた。押しても何も起きないように見える。
原因2 <a download> は iOS では「写真」ではなく「ファイル」アプリに入る。 写真アプリに入れる道は、共有シートか、画像の長おし →「写真に追加」しかない。
対処 画面の中身が変わるたびに、裏で PNG を作って持っておく（止まってから0.5秒後）。 押した瞬間には待ち時間ゼロで共有シートを呼べる。あわせて 「携帯に入ってこないときは」を常に置き、押すと できあがった画像そのものを大きく出す。ここに置くのは <canvas> ではなく <img>（長おしのメニューが出るのは img だけ）。 例外も AbortError（利用者が閉じた）とそれ以外で分け、 それ以外のときは必ず逃げ道を出す。
教訓 「保存」を押したあと、何も起きないまま終わる道を1本でも残さないこと。 失敗したことすら分からないのが、いちばん直しようがない。
CASE 13 画面いっぱいのはずのシートが、カードの中に閉じこめられる
原因 position: fixed は「画面」を基準にするが、 transform のかかった親がひとつでもあると、その親を基準にしてしまう。 ステップ3のカードには出現アニメーション（transform）が掛かっているので、 その中で開いたシートは「画面いっぱい」のつもりでカードの中の四角になる。
見つけかた DOM にはあるし、目にも見えている。Playwright の toBeVisible も通る。寸法を測るまで気づけなかった （390×900 のはずが 356×774 @(17,77) ＝ カードの箱そのもの）。 スクリーンショットを撮って初めて「おかしい」と分かった。
対処 共通部品 Sheet の中で createPortal して body 直下に出すようにした。呼ぶ側は場所を気にしなくてよくなる。 検証には「本当に画面をおおっているか」を寸法で見る項目を足した。
同時に見つかったこと 新しいシートに .sheet__* というクラス名を付けたら、 すでにあった「つかいかた」のシートの CSS と名前がぶつかり、 関係のない画面のほうが壊れていた（あとに書いたほうが勝つ）。 新しいほうを .saver__* に改名し、 「つかいかたも画面ぜんぶをおおうか」を検証に足した。
CASE 17 どのページを開いても、AI の実行環境が落ちてきていた
きっかけ 素材の重さを測っていて、飾りを全部足しても 690KB なのに ページの合計が 1.1MB を切らないことに気づいた。1件ずつ並べたら、 855KB の ai-*.js が3ページとも先頭に出てきた。 切り抜きの画面へ一度も行っていない、応援ページやお礼ページでも。
原因 vite.config.ts に 「@huggingface/transformers と onnxruntime を ai という塊にまとめて、必要になるまで読み込ませない」という manualChunks を書いていた。 ところがその塊に、Vite が動的 import のために使う 200バイトほどの 補助関数まで一緒に入った。補助関数のほうは入口の側からふつうに import されるので、入口が 855KB の塊を静的に 参照する形になり、index.html に modulepreload まで付いた。 まとめる指示が、まとめたくないものを引き寄せていた。
なぜ気づけなかったか 画面は正しく動く。余分に落ちてくるだけで、見た目も操作も何も変わらない。 切り抜きも通る。検証も全部通る。 見ても分からない種類のこわれかたで、測って初めて分かる。 しかも「AI は必要になるまで読み込まない」と自分で書いたコメントが すぐそこにあるので、読み返しても正しく見える。
対処 manualChunks を消した。動的 import は、 まとめる指示を書かないほうが意図したとおりに分かれる （lib/ai.ts と transformers.web が別々に出る）。 あわせて検証に「開いただけで重いものを落とさない」を足した ——1件400KBを超えるものを落とさない／最初に落ちてくる合計が1MB未満。 同じことが起きたら、次は測らなくても落ちる。
つくる 1.11MB → 0.28MB  ／  応援 1.67MB → 0.83MB  ／  お礼 1.54MB → 0.71MB
CASE 16 Android で、共有シートを主役のボタンにしていた
原因 共有できる端末なら共有シートを大きいボタンにする、という作りにしていた。 これは iPhone を基準にした思い込みで、 Android の共有シートには保存の項目が無い。 実機で開いてもらったら、Gmail / Instagram / 画像をコピー / QR コードしか 並んでいなかった。押しても1枚も保存できないボタンが、 いちばん目立つ場所に置かれていたことになる。
正しい対応関係 iPhone は共有シートに「画像を保存」があり、写真アプリに入れる道はそこだけ （ダウンロードは「ファイル」アプリ行き）。Android はその逆で、 保存できるのはダウンロードのほう。つまり正反対。
対処 端末を見て、大きいボタンの中身を入れ替える。iPhone は共有、それ以外はダウンロード。 もう片方は下に小さく残し、Android 側の共有には 「（保存ではありません）」と書き添える。 あわせて、Android では共有が成功しても「保存しました」と出さないようにした （共有できた＝保存できた、ではない）。
検証 実機を並べられないので、UA を iPhone に差し替えて navigator.share を生やしたページで判定の分かれ目を押さえている。 「共有できない端末では『画像をほぞんする』が主役」 「iPhone では『写真アプリにほぞんする』が主役」の2つ。
CASE 15 お試しリンクだと、保存できましたと出るのに1枚も落ちてこない
原因 <iframe sandbox> の中では、ブラウザが ダウンロードそのものを止める（allow-downloads が要る）。 共有も同じく止まる。やっかいなのは <a download> が 例外を投げないことで、こちらからは成功したように見える。 結果、「保存できました」の緑の案内だけが出て、ファイルは1枚も無い。
対処 window.self !== window.top で枠の中にいることは分かる。 そのときは「保存できました」と言い切らず、 長おしできる画像のシートを開き、「いま別のサイトの中で開かれています」と 事情のほうを説明する。あわせて、成功時の文面も 「保存できました！」から「保存しました。見あたらないときは…」に変えた。 こちらから見えているのは「保存をはじめた」ところまでで、 端末に入ったかどうかは分からない。分からないことを断定しない。
検証 検証用サーバーに /__embed を足して、 allow-downloads の無いサンドボックス iframe の中で 実際に通しに動かしている。「緑の案内を出さないこと」「かわりに 長おしできる画像を出すこと」を機械で押さえた。
運用 お試しリンクは動作確認に使えない。 保存まわりを試すときは、公開した本物の URL を開くこと。
CASE 14 直したはずの画面が、いくら直しても変わらない
原因 型チェックのつもりで tsc にオプションを付けて叩いたとき、 src/ の中に コンパイル結果の .js が吐き出されていた。 Vite は ./ComposeStudio を解決するとき .js を先に見るので、 以後ずっとその時点で凍った古い画面がビルドされ続ける。
症状 .tsx を直す → ビルドは成功する → 画面は変わらない。 検証も「古いほうの画面」に対して通るので、緑のまま嘘をつく。
対処 src/**/*.js を .gitignore に入れて、 混ざったらすぐ git clean -f src/ で落とせるようにした。 型チェックは npm run typecheck を使うこと （素の tsc にオプションを足して叩かない）。
見分けかた 直したはずのものが反映されないときは、まず find src -name "*.js"。1つでも出てきたら、これを疑う。

お金のこと

応援（チップ）

ツールは無料のまま。「気持ちだけ渡したい」という人の受け皿だけを用意してあります。 src/tip-config.ts の URL が空のあいだは、応援の案内は画面のどこにも出ません。 設定しなければ、ただの無料ツールとして成立します（そのことも検証で押さえてあります）。

置き場所は2つだけ

保存できた直後
画像が手に入った、そのすぐ下。閉じたらそのセッションでは二度と出ません。
フッターの小さいリンク
いつでも出ています。上を閉じた人が、あとから自分で探せる場所。

言いかたで決めたこと

  1. 受け取る前にお願いしない

    まだ何ももらっていない人へのお願いは、ただのお願いです。欲しいものが手に入った 直後なら、こちらから言わなくても「これ無料でいいの？」と思ってもらえる瞬間がある。 そこにだけ置きます。

  2. 押さないことを気まずくしない

    「ずっと無料です」「押さなくても、何も変わりません」を先に書き、 閉じるボタンを必ず添えます。閉じたら、そのセッションではもう出しません。

  3. お金の話は正直に短く

    どこへ飛ぶのか、カード情報がどこを通るのかを、押す前に書いておきます。

Stripe の設定（10分ほど）

このツールはサーバーを持たない静的サイトです。ふつうの Stripe 決済はサーバー側の処理が 要りますが、支払いリンク（Payment Links）なら Stripe の決済ページに 飛ばすだけなので、サーバーが要りません。 カード番号はこのサイトを一切通りません。

  1. アカウントを作る

    dashboard.stripe.com/register から。日本の個人でも作れます （本人確認と振込先の口座が要ります）。

  2. 応援用の商品を1つ作る

    「商品」→「商品を追加」。名前の例：「アイコンフレーム メーカーへの応援」。

  3. 金額ごとに支払いリンクを作る

    「支払いリンク」→「新規作成」→ 上で作った商品を選ぶ。100 / 300 / 500円など。

  4. 金額を相手に決めてもらうリンクも1つ

    価格を作るときに「顧客が金額を指定できるようにする」を選ぶと作れます。

  5. できた URL を貼る

    https://buy.stripe.com/... の形。貼り先は src/tip-config.ts の TIP_OPTIONS と TIP_CUSTOM_URL だけです。

  6. テストしてから本番に差し替える

    ダッシュボードをテストモードにしてリンクを作り、 4242 4242 4242 4242／有効期限は未来の日付／CVC は任意 で通しを確認。 本番で使うときは、テストモードを切って作り直したリンクに差し替えます。

先に知っておくこと

  • 手数料は日本のカードで 3.6%（2024年時点。最新は Stripe の料金表で）。 100円の応援なら手元に残るのは96円ほど。少額を並べすぎると手数料負けします。
  • 受け取ったお金は所得です。金額によっては確定申告が要ります。
  • 見返り（特典）を約束しないこと。 約束すると商取引になり、特定商取引法の表示義務などが発生します。 「対価のない任意の支援」の形を保ってください。

お金の受け皿

応援ページと、お礼のページ

#/support で金額をえらび、Stripe の決済ページへ渡す。 決済のあとは #/support/thanks に戻ってくる。 

つくる → 保存 → 応援(#/support) → Stripe → お礼(#/support/thanks) → またつくる

輪になっているのが大事なところ。お礼のページを「決済ありがとうございました」で 終わらせると、そこで人が止まる。だからいちばん大きいボタンは「もう1個つくる」。

崩してはいけない約束

  • カードを選んだだけでは、どこへも飛ばない。 選ぶ操作と、お金の話へ進む操作を分けてある。指が当たっただけで 決済ページに飛ぶのは、いちばんやってはいけない類の事故なので。
  • カード番号の入力欄を1つも作らない。 決済は Stripe の画面でだけ起きる。シークレットキーも使わない （そもそもフロントエンドに置けるものではない）。
  • 保存直後の案内では金額を出さない。 できた！を味わう場所に金額のカードを4枚並べると、会計の画面になってしまう。
  • URL は src/tip-config.ts にだけ書く。 画面の側に貼らない。金額を変えるときに探し回らずに済む。

なぜハッシュ（#/support）なのか

GitHub Pages には「どのURLでも index.html を返す」設定が無い。 ふつうのパス（/support）で直リンクを配ると 404 になる。 ハッシュならサーバーから見ればいつも同じ1枚なので、必ず開ける。 画面は3つしかないので、ルーティングのライブラリは入れていない。

つくる画面は、応援ページへ寄り道しても外さずに隠しておく。 写真もフレームも手でなおした跡も、ここで消えると 「応援したせいで作りかけが消えた」ことになる。

素材

public/assets/support/ に7枚。 置いていなくてもページは完全に動く（飾りが出ないだけ）。 飾りは CSS の背景として敷いてあるので、ファイルが無ければ何も起きない。 意味のある絵（ハリネズミ）だけ <img> にして、 読み込みに失敗したら枠ごと畳む。

飾りの URL はスタイルシートではなく、要素の style で渡している。 ビルドすると CSS は dist/assets/ の中に置かれるので、 そこに書いた ./assets/... は assets/assets/... を 指してしまう。

Stripe 側で、人がやること

各支払いリンクの「支払い後」の遷移先に、公開URL＋#/support/thanks を設定する。ここはダッシュボードの設定なので、コードからは変えられない。

確かめかた

検証

npm test は実際に Chromium を起動し、画像を読み込ませて、 出力画素のアルファを読んで判定します。透過の良し悪しは目で見ないと分からないと 思われがちですが、次のことは機械的に確かめられます。

  • 四隅とまん中の穴が透明になっているか
  • うすい色のリングが、半透明にならず残っているか
  • 囲まれた白（提灯の紙・狐面・泡）に穴が開いていないか
  • グローが階調のまま残っているか（半透明画素の割合で測る）
  • 暗い写真に重ねたとき、グローが色を保っているか
  • 透過ずみの画像で、半透明部分の色が変わっていないか
  • スクショから UI が落ち、正方形に近く切り出されているか
  • AI を呼ぶべきとき／呼ばずに済むべきとき、それぞれ正しいか

検証用の画像は tests/fixtures.mjs がその場で描き起こします。実物の見た目を似せたものではなく、 つまずく性質だけを取り出したものです。

本物のフレームで確かめる

tests/real/ を作って自分のフレーム画像（png / jpg / webp）を放り込んでから npm test すると、1枚ずつ通して四隅・まん中の穴・面積比・エラーの有無を確かめます。 .gitignore 済みなので、フレームがリポジトリに入ることはありません。 画像を置かなければ、この項目は黙って飛ばされます。

新しいデザインで不具合が出たら、まずここに置いて再現させてください。 直したあと、その性質だけを取り出した画像を tests/fixtures.mjs に足せば、 以後は自動で守られます。上の CASE はすべてこの手順で固定しました。

正直なところ

わかっている制限

AI切り抜きの実地確認ができていません。 開発環境が huggingface.co を遮断しているため、モデルの取得から推論までを通しで動かせていません。 読み込みに失敗したときに色キーへ落ちる経路は確認済みなので行き止まりにはなりませんが、 公開後に一度、白いガラス系のフレームで確かめてください。

  • iPhone では振動しません。 iOS Safari が Vibration API を持っていないためです。 非対応端末ではスイッチ自体を出していません。iPhone では音と見た目だけで手ざわりを作っています。
  • HEIC はブラウザ次第です。 iOS の写真アプリから選ぶと多くの場合 JPEG に変換されますが、 HEIC のまま渡されてデコードできない環境では、日本語で「保存しなおしてください」と出します。
  • AIモデルのライセンス。 既定の1番手 RMBG-1.4 は非商用の条件付きです。 無料で配る用途なら問題になりませんが、商用にするなら src/lib/ai.ts の MODELS の順番を入れ替えて、MIT の BiRefNet を先頭にしてください。
  • 真っ白を白地に描いたデザインは、色では原理的に分けられません。 色差が 0.008 を下回ると背景と区別できないので AI に回ります。AI でも詰めが甘ければ、 「消しのこりを消す／消えすぎをもどす」の筆で仕上げる想定です。
  • SNSに貼ったときの絵が、まだ出ません。 タグは実装ずみですが、public/og-image.png（1200×630・透過なし）が まだ置かれていないので、カードは画像なしで表示されます。 ファイルを1枚置けば、それだけで効きます。
  • 素材に市松模様が焼き込まれているものがあります。 「とうめい」の目印が絵として塗り込まれた状態 （白 254 と薄灰 247 が交互）。いまは CSS で打ち消していますが応急処置です。 書き出しのときに「背景を含める」を切れば要らなくなります。
  • 応援の決済は、実際のお金では通していません。 Stripe のアカウントを作れるのは本人だけなので、こちらで確かめられたのは 「URL が空なら案内が一切出ない」「入れれば正しいリンクへ飛ぶ」ところまでです。 本番のリンクを貼ったら、テストモードのカードで一度だけ通してください。
  • オフライン対応はしていません。 Service Worker は入れていません。

設計の詳しい理由は README.md に、実装上の判断はコード中のコメントに残してあります。 迷ったら、まず src/lib/cutout.ts の冒頭のコメントを読んでください。

方針としてひとつだけ： 推測より、出した結果を測ること。 上の CASE はすべて、頭で考えた判定が実物の前で外れた記録です。
