# チップを戻すときの計画

`docs/stripe-compliance.md` は「なぜ外したか」と「戻すとき何を満たすか」の記録。
こちらは、それを**どの順番で、誰が、何をするか**に落としたもの。

> **サイト側の実装は入った。決済リンクはまだ0本。**
> 送り先（`TIP_URL`）が空のあいだ、入口も文言も配るものに入らない。
> Stripe 側の手順は `docs/tip-stripe-setup.md`（渡す用に切り出してある）。

**筆者は弁護士でも税理士でもない。** 下の法令まわりは、確認すべき論点の整理であって、
判断そのものではない。金額が動く前に、専門家か、書面での公式回答を取ること。

---

## 0. まず決めること：サイトに置くのか、置かないのか

戻す前に、そもそも**このサイトに置く必要があるか**を一度考える。

| どこに置くか                       | 手間                 | 止められる危険                                       |
| ---------------------------------- | -------------------- | ---------------------------------------------------- |
| このサイト（Stripe）               | 事前確認・文言・検証 | 一度照会を受けた口座。もう一度当たると次は重い       |
| 配信プラットフォーム側のギフト機能 | ほぼ無し             | プラットフォーム側の規約だけ。こちらの口座に及ばない |
| 外部のチップ用サービス             | 登録のみ             | サービスによっては「これから作るもの」前提の作り     |

**いちばん危険が小さいのは、サイトに置かないこと。** フレームを配っている場所には
もともとギフトの仕組みがある。そちらで足りるなら、この計画は不要になる。

外部サービスを使う場合は、そのサービスの**建てつけ**を見る。
「これから作るものを支える」形（月額の支援・目標額・支援者向けの限定物）は、
Stripe が引っかかったのと同じ構造なので、乗り換えても同じ話になる。
選ぶなら「もう受け取ったものへのお礼」を単発で送る形のもの。

以下は「それでもこのサイトに置く」と決めた場合の手順。

---

## 1. 先に Stripe に聞く（リンクを作るより前）

### Stripe が実際に言っていること（一次情報）

サポートの「チップまたは寄付を受け付けるための要件」に、こう書かれている。

- **チップ**は、**すでに提供した商品またはサービス**に対して支払われるものでなければならない
- **寄付**は、**果たすと約束した特定の慈善目的**に紐づいていなければならない
- 本物の商品・サービスの販売も、寄付の受け取りも無い決済は扱えない
- 個人間の送金には使えない

つまり、こちらが選ぶのは**チップ**。「寄付」と名乗ると、慈善の目的を
約束することになり、この道具はそれに当たらない。
**画面でもStripeの設定でも「寄付」という語を使わない。**

「すでに提供したサービス」は、この道具そのものがそれに当たる。
無料で公開して、もう使ってもらっている。**将来に触れなければ、これで足りる。**

一度「規制対象業種のいずれかに関連する」と判断された口座なので、黙って再開しない。
**書面で聞いて、書面で返事をもらう。**

聞くときに出すもの：

1. このツールが何か（無料・全機能・端末内処理・販売物なし）
2. 受け取りたいお金が何か（**すでに使ってもらったことへの、任意のお礼**）
3. 見返りが無いこと（払っても機能は1つも変わらない）
4. 実際の文言（下書きの全文）
5. 公開URL

聞くこと：

- この形で受け取ってよいか
- 使うべき商品（Payment Link / Checkout など）の指定があるか
- 表示すべき事項の指定があるか

**返事が来るまで、リンクは作らない。** 前回は「画面から消した」で止めて、
配られる JS の中に文言が残っていた。順番を守るのは、そのときの学びの続き。

## 2. 文言の下書き

満たすものは4つ（`docs/stripe-compliance.md`「戻すときの条件」）。
言い換えると、**書いてよいのは過去のことだけで、渡せるものは何も無い**。

### 書くこと

```
このツールは全部無料です。これからもそうです。
使ってみて、もし気が向いたときだけ、お礼を送れます。

払っても、機能は1つも増えません。
払わなくても、全部そのまま使えます。

（金額の選択）
```

### 書かないこと（と、その理由）

| 書かない                               | なぜ                                           |
| -------------------------------------- | ---------------------------------------------- |
| これから何を作るか                     | 将来の成果物に触れた時点で資金集めになる       |
| お金の使いみち                         | 同上。「〜に使います」は目的のある集金に読める |
| 目標額・期限・達成度                   | 同上。クラウドファンディングそのもの           |
| 払った人の一覧・特典・先行・限定       | 見返りを約束すると、寄付ではなく販売になる     |
| 「支える」「続けられます」系の言い回し | 継続の支援＝これからのぶん、と読める           |

禁止語の正は `tools/check-dist.mjs` の `BANNED_WORDS`。
**リストを消して通す、をしない。** リストに当たらない文章を書く。

### 用語

`support` は使わない（旧URL・旧クラス名がそのまま残っており、
古い検証や置換とぶつかる）。新しい語にする。ページも `#/support` は使わない
——あれは共有ページへ送る転送先として予約済みで、戻すと転送とぶつかる。

## 3. 法令まわりで確認すること

### 特定商取引法

消費者庁のガイドに書かれていること。

- 表示義務がかかるのは**通信販売**、つまり対価を取って商品・特定権利・役務を売るとき。
- **個人であっても**、要件を満たせば「販売業者（役務提供事業者）」に当たる。
  法人だから／個人だから、で決まるものではない。
- 表示するのは、販売価格（役務の対価）・送料・支払方法・引渡し時期・
  返品の可否と条件・**事業者の氏名（名称）・住所・電話番号**。
  住所と電話番号は「通称やサイト名では足りない」と明記されている。

こちらの整理は「**渡すものが1つも無いので、売っていない**」。
だから表示義務の話に入らない。

前回、この結論に至る道が間違っていた。「対価にしないために、これから作るものの
話にする」としたので Stripe に当たった。**対価を消すのに、将来へ逃げる必要は無い。**
「何も渡さない」と書けば足りる。Stripe の要件とは同時に満たせる。

**この整理は、見返りを作った瞬間に崩れる。** 払った人だけの機能を1つでも
足したら、そこから先は販売で、住所と電話番号を公開する話になる。
だから「払っても何も変わらない」は遠慮ではなく設計であり、
検証で毎回見ている（つくる画面が入口の有無で1文字も変わらないこと）。

### 住所を出さずに済む道が、他にもあること

もし将来「対価あり」の形にするなら、自前サイト＋Stripe 直では
住所・電話番号の公開を避けられない。Stripe は決済代行であって販売業者ではないので、
代わりに表示してはくれない。

一方、**プラットフォーム経由**なら別の道がある。クリエイターエコノミー協会が
消費者庁・経済産業省と協議した結果、プラットフォームが出品者の現住所と
電話番号を把握していて、消費者が確実に連絡を取れる体制があるなら、
表示はプラットフォームの住所・電話番号でよい、という消費者庁の見解が出ている
（BASE や minne が非公開機能として実装している）。

つまり選択は「対価なしで自前」か「対価ありならプラットフォーム」。
**自前サイトで対価あり**が、いちばん高くつく組み合わせ。

- ただし、実際に義務がかかるかは書きかたと運用で変わる。**公式に確認する。**

### 税

- 個人が受け取る任意の金銭は、金額と継続性しだいで扱いが変わる。
- 「毎月このくらい入る」形になるほど、ただの贈与では済まなくなる。
- ここは調べて分かる話ではないので、**税理士に聞く**。金額が動く前に。

### AIモデルのライセンス（見落としやすい）

既定の1番手 RMBG-1.4 は**非商用**の条件付き。
無料で配っているだけなら問題にならないが、口座にお金が入る形にすると、
「商用か」を自分で判断することになる。

**争うより避けるほうが安い。** チップを入れるなら、同じ変更のうちに
`src/lib/ai.ts` の `order()` の既定を `'alt'` 側にして、MIT の BiRefNet を
先頭にする。1行で済むようにしてある。

## 4. 画面のどこに置くか

**保存できた直後には置かない。**

前はそこに置いていた。`ComposeStudio.tsx` にその判断の跡が残っている——
保存できた人にいちばん要るのは次の作業への道であって、お願いではない。
いまその場所には「フレームを人にわたす」と「つぎにどうする」が入っている。
そこへ割り込ませると、**この道具でいちばん多い次の行動を、お願いが押しのける**。

置くのは、いま「このツールを人に知らせる」がある**下の静かな場所**。

### 押しどころは増やさない

`styles.css` の冒頭に決まりがある——強調色は「いま押すところ」1か所だけ。
検証にも、1画面に強調色のボタンと警告の地が合わせて1つしか無いことを数える項目がある
（`■ どれを押せばいいか`）。

チップの入口を強調色にすると、この検証が落ちる。**落ちたら、上限を上げずに設計を直す。**
入口は `link-quiet` と同じ静かさで置く。

## 5. 作りかた（実装ずみ）

- 決済リンク1本を新しいタブで開くだけ。フォームも、金額の計算も、こちら側に持たない。
- 戻り先ページは作らない。前回、決済のあとのお礼ページと、そこへの順路が
  いちばん目立つ形で残っていた。**画面を1枚増やすと、消すときに1枚忘れる。**
- 送り先（`TIP_URL`）が空なら、入口ごと消える。

### 「空なのに文言が残る」を、条件分岐で防がないこと

前回の穴はここだった。募集の文言を `if` の向こうに置いて「画面に出ない」で
止めたが、**文字列は配られる JS にそのまま残っていた。**

今回、同じことを1回やり直している。footer に

```
{TIP_ON && <button>作った人にお礼を送る</button>}
```

と書いたら、送り先が空のビルドにも「作った人にお礼を送る」が入っていた。
ページ本体は別ファイルにして外せていたのに、**呼ぶ側の1行で漏れた。**

条件分岐は、束ねる側の気分しだいで残る。残ったかどうかは目で見ても分からない。
なので**モジュールの解決そのものを差し替える**ことにした
（`vite.config.ts` の `ae-frame:tip-entry`）。送り先が空なら、
`src/components/Tip.tsx` はモジュールの地図に一度も現れない。入りようがない。

**出したくないものは、リンクの1行まで全部あちら側に置く。**

## 6. 検証（入れずみ）

状態が2つあるので、**2本ビルドして両方見る**。
入りの側は `example.com` のダミーで、本物の決済リンクは1本も要らない。

`tools/check-dist.mjs`（配るものを直接読む）

- `BANNED_WORDS` はそのまま。新しい文言はこれに当たらないように書いてある。
- 空のビルド：お礼の文言が**1つも**入っていないこと
- 入りのビルド：お礼の文言が**全部そろって**いること、送り先が入っていること
- 決済リンクの数えかたも状態で切り替える。空なら0本、入りなら**その1本だけ**。
  「0本」で固定すると、入れたときにただ落ちるだけになり、緩めて黙らせたくなる。
  緩めた瞬間、2本目が入っても気づけなくなる。

`tests/run.mjs`（画面の側から）

- 空のとき：足もとに入口が出ない／`#/tip` はつくる画面になる／文言が0個
- 入りのとき：入口が出る／断りの文が出ている／押しどころは1か所／
  押すと決めた送り先だけが開く／危ない言いかた（寄付・支援・特典など）が出ない
- **つくる画面が、入口の有無で1文字も変わらないこと**（1枚目と、重ねて保存の画面）。
  払わない人が損をしていない、を画面の差分で見る。ここがいちばん大事な1件。

新しく足した項目は、**壊して落ちることを1つずつ確かめてから**入れている。

## 7. 出す順番

`docs/stripe-compliance.md` の「公開の順番」と同じ。**コードではなくサイトを先に直す。**

1. `npm run build && npm test` を通す
2. GitHub Pages へ反映する
3. 公開URLを開いて、目で確かめる
4. そのうえで Stripe へ出す

逆にすると、審査中に古いものを見られる。一度やりかけている。

---

## 8. やらないと決めていること

- Git 履歴の書き換え（過去のコミットには古い決済リンクが残るが、
  公開済みリポジトリで履歴を書き換えると別の面倒を呼ぶ）
- Stripe 側の操作（リンクの作成・復旧・アーカイブ解除）
- 事前確認が済む前の実装
