# フレームを、誰でも作って配れるようにする（計画）

**やりたいこと**（相談のことば）

> アイコンフレームを登録して、それをみんなに共有して、固定されたアイコンフレームに
> 自分が持っている画像を配置できるようにしたい。
> みんなアイコンフレームつける時にバラバラになっちゃうことを懸念して。
>
> 誰でも登録して配れるようにしたい。それぞれの枠のフレームがあると思う。

**決まったこと**：**誰でも**作って配れる。運営が1枚ずつ入れる形にはしない。
配信枠ごと・イベントごとに1枚ずつ、短い期間に数多く生まれる想定。

---

## 0. 「バラバラになる」の中身は、2つある

ここを分けないと、作るものを間違える。

| 何がバラバラになるか                 | いまの状態                                             |
| ------------------------------------ | ------------------------------------------------------ |
| ① 違うフレームを使う                 | 半分解決ずみ（透過PNGを手渡しできる）                  |
| **② 同じフレームでも置きかたが違う** | **1つも手を打っていない**                              |

3つめの画面は、写真を **cover（画面いっぱい）から始めて自由に動かす**作り。
しかも「指でうごかす／2本でひろげて大きさ」と画面が誘っている。
**同じフレームを配っても、全員が別々に動かす。**

→ **配るしくみだけ作っても、そろわない。** 置きかたを一緒に配る必要がある。

---

## 1. 配る単位は「画像」ではなく「画像＋置きかた」

これがこの計画の中心。フレームのPNGだけ渡しても、そろわない。

```json
{
  "v": 1,
  "name": "○○の枠",
  "hole": { "cx": 0.5, "cy": 0.5, "r": 0.34 },
  "lock": { "move": "hole", "rotate": false, "gap": "white", "round": true }
}
```

| 鍵       | 意味                                                          |
| -------- | ------------------------------------------------------------- |
| `hole`   | 写真を入れる窓。フレーム画像に対する**比**（画素では書かない）|
| `move`   | `hole`＝穴の中でだけ動かせる／`free`＝自由／`none`＝動かせない |
| `rotate` | かたむきを触らせるか                                          |
| `gap`    | すきまの色を固定する                                          |
| `round`  | まるく切りぬくを固定する                                      |

**全部を禁止しない。** 穴の中での移動と拡大は残す。
そこを取り上げると、顔が切れた人が直せなくなる。
そろえたいのは**フレームの見え方**であって、中身の人ではない。

## 2. 段階0 —— 写真を、フレームの穴に自動で合わせる

**これは「あとで嬉しい機能」ではなく、上の `hole` を作るための前提。**
穴の場所が分からなければ、置きかたを固定しようがない。

### 穴の場所は、すでに計算してある（捨てているだけ）

`src/lib/cutout.ts` の `floodBackground` は、背景を消すときに
**画像の中心からも種を蒔いている**。リング状フレームの「まん中の穴」を
抜くためで、そうしないと重ねたときに写真が隠れるから。

```
種は2か所から蒔く。
 - 画像の四辺 … 外側の背景
 - 画像の中心 … リング状フレームの「まん中の穴」
```

### やること

1. 背景を消したあと、**穴の外接する円（または矩形）**を比で求めて持ち回る
2. 3つめの画面の初期値を、cover ではなく**その穴にぴったり入る倍率・位置**にする
3. 穴が見つからないフレームは、いままでどおり cover

### これだけで何が変わるか

- **ほとんどの人が、もう動かさなくてよくなる。** 動かさなければズレない
- **いま手渡しでPNGを配っている人たちにも、その日から効く**
- そして `hole` が取れるので、段階1 の土台になる

---

## 3. 段階1 —— フレームのファイルに、置きかたを焼きこむ（サーバー不要）

**誰でも・即時・無料。これで「誰でも登録して配れる」は満たせる。**

### 実物で確かめた

PNG には、絵に影響しない文字を入れる決まった場所（`tEXt` チャンク）がある。
そこに上のレシピを入れる。

```
元のPNG       274500 バイト
焼きこんだ後  274628 バイト   (+128 バイト)
読み戻し      完全一致
ふつうの画像として  900x900 で問題なく開ける
```

**128バイト。** 実質ただ。しかも読めない道具から見れば、
ただの透過PNGのまま（`tEXt` は無視してよい決まりの領域）。

### 配りかた

```
作る人   : フレームを作る → 保存する → Discord / LINE に「ファイル」として送る
もらう人 : そのファイルをアプリに渡す → 置きかたは決まっている → 自分の写真 → 保存
```

**登録も審査も要らない。** 作った人が配る。運営は何も預からない。

### 手順が減る

```
いま        ① 写真 → ② 背景をけす → ③ 位置をあわせて保存
配られた人  ① 写真 →              → ② 位置（固定）→ 保存
```

もう透過ずみなので、**背景けしの画面が丸ごと要らなくなる。**

### すでにある注意書きが、そのまま効く

3つめの画面には、もうこう書いてある。

> とうめいは、送りかたで消えます。LINE や SNS に「写真」として送ると、
> とうめいのところが白や黒で埋まります。そのまま渡したいときは、
> **「ファイル」として送る**か、いちど保存してから渡してください。

**焼きこんだ置きかたも、同じ条件で残る／消える。**
「写真」として送られて再圧縮されれば、透過もレシピも一緒に飛ぶ。
利用者に覚えてもらう決まりが増えない。

### 弱いところ（隠さない）

- **リンクではなくファイル。** スマホだと、Discordから落として選び直す手間が要る
- 誰かが別の道具で開いて保存し直すと、レシピは消える（ただの透過PNGに戻る）

## 4. 段階2 —— リンクで配る（ここで初めて置き場所が要る）

段階1 で足りなければ。**ここからは、預かる話になる。**

### なぜリンクにするには置き場所が要るのか（実測で確認）

「リンクの中に画像を全部入れる」は成り立たない。

- フレームのPNGは実測 **30〜270KB**。base64 で 1.33倍 → **40〜360KBのURL**
- **Discord のメッセージ上限は2000文字**。入るのは 1.4KB ほど。桁が2つ足りない
- QRコードの上限は約3KB。同じく足りない
- 256px まで落とせば20KB程度に収まるが、書き出しは900px。**ぼやけたフレーム**になる

**貼って配れないリンクは、共有機能として意味が無い。**
だから、リンクにするなら画像はどこかに置くしかない。

### 落とした案：作った人が自分でURLを用意する

- 置き場所を持っている配信者はほとんどいない（「誰でも」にならない）
- CORS が通らない置き場所が多い
- **URLに何でも書ける。** 他人の画像を「このツールのフレーム」として開かせられる

### 置き場所を借りるときの設計

預かる以上、**見つけられる場所にはしない。** 作るのは「配る道」であって「並べる棚」ではない。

| 決めること       | こうする                                                     |
| ---------------- | ------------------------------------------------------------ |
| 一覧・検索       | **作らない。** リンクを知っている人だけが開ける              |
| 期限             | **切る**（例：90日）。「枠ごと」なら期限があるほうが自然     |
| 消しかた         | 運営が消す（`wrangler kv key delete`）。**作った人が自分で消す道は作っていない**（理由は手順書） |
| 通報             | **済**。すでにある窓口を使う（kazuworks.net/contact）。新しく作らない |
| 規約             | **済**。畳まず、「リンクを作る」の直前に2行で置く            |
| 費用             | 無料枠のある置き場所を比べる（**本当の費用はお金ではなく人手**）|

**一覧を作らないのがいちばん効く。** 棚に並べた瞬間、
「集めて見せている場所」になり、話がまるごと変わる。

## 5. 法律の話（前回の記述を訂正する）

前回この文書に「プロバイダ責任制限法の削除対応、通報の受け口が要る」と書いた。
**重すぎた。訂正する。**

調べ直したところ、削除申出への**7日以内の判断・通知**や、
**運用状況の公表**（削除件数、モデレーターの人数など）といった重い義務は、
2025年4月施行の情報流通プラットフォーム対処法で
「**大規模**特定電気通信役務提供者」に課されるもの。

- 指定の目安は **平均月間発信者数1000万人**
- 2025年4月に指定されたのは **Google / LINEヤフー / Meta / TikTok** の4社

**この道具は桁がいくつも違う。これらの義務は当たらない。**

規模に関係なく残るのは、だいたい次のところ。

- 権利侵害を**知りながら放置する**と、免責が外れて責任を問われうる
- 発信者情報の開示を求められる場面がありうる

つまり実務で要るのは、**連絡が取れること**と、**言われたら消せること**。
規約と窓口があれば足りる。前回書いたような常時の体制は要らない。

> これは公開資料を読んだ範囲の整理で、法律の助言ではない。
> お礼（チップ）を受け取っている口座がある以上、段階2 に進むと決めたら、
> 規約の文面は一度どこかで見てもらったほうがよい。

出典：
[総務省・情報流通プラットフォーム対処法](https://www.soumu.go.jp/main_sosiki/joho_tsusin/d_syohi/ihoyugai.html) ／
[大規模特定電気通信役務提供者の指定（報道資料）](https://www.soumu.go.jp/menu_news/s-news/01ryutsu02_02000440.html)

### 現実に起きるのは、法律よりも先に「これ、うちのキャラだよね」

配信者向けのフレームは、アニメやゲームの絵を元にしたものが多い。
**段階1（ファイル）なら、運営は何も預からないのでこの話が起きない。**
段階2 に進むと、預かった瞬間から起きうる。

段階1 を先に出すのは、遠回りではなく**この順番に意味がある**ということ。

## 6. 順番

| #  | やること                                             | 大きさ | サーバー | 状態     |
| -- | ---------------------------------------------------- | ------ | -------- | -------- |
| 1  | **穴に自動で合わせる**（段階0）                      | 中     | 不要     | **済**   |
| 2  | レシピの形を決める（`hole` / `lock`）                | 小     | 不要     | **済**   |
| 3  | 保存するPNGにレシピを焼きこむ                        | 小     | 不要     | **済**   |
| 4  | 渡されたPNGからレシピを読んで、置きかたを固定する    | 中     | 不要     | **済**   |
| 5  | 配られた人の画面（2ステップ）                        | 中     | 不要     | **済**   |
| 6  | 実際に1枚作って、Discord で配ってみる                | 小     | 不要     | これから |
| — | **ここまでで「誰でも作って配れる」は完成**             |        |          |          |
| 7  | 置き場所・期限・通報窓口・規約                       | 大     | **要る** | **実装済**（置き場所の用意だけ残り） |
| 8  | `#/f/<id>` のリンクで開く                            | 中     | 要る     | **済**   |

**7 の「置き場所を用意する」だけが残っている**（`docs/frame-link-setup.md`）。
`FRAME_API` を設定するまで、リンクまわりは画面に1つも出ない。

### リンクで配る形（7〜8）

```
配る人 : そろえる → 名前をつける →「リンクを作る」→ リンクを配る
もらう人: リンクを押す → 写真をえらぶ → 保存                （3手）
```

受け口は https://kazuworks.net/contact（本人確認ずみ。メールが届く）。

### 1〜5 でできあがった形

```
作る人   : フレームを作る → 「みんなの見た目をそろえる」を入れる
           → 保存 → Discord / LINE に「ファイル」として送る
もらう人 : そのファイルをフレームとして渡す
           → 背景けしを通らず、位置あわせへ直行
           → 写真の位置と大きさだけ決める → 保存
```

固定するのは**フレームの見え方**（すきまの色・まるく切りぬく・かたむき・
フレームの置き場所）。**写真の位置と大きさは相手に残す。**
顔の入れかたまで奪うと、顔が切れた人が直せなくなる。

固定された項目は、画面から**消す**。押せないものを見せない。
代わりに「なぜ少ないのか」が分からなくなるので、理由を1行置いてある。

検証は「作った人と、もらった人が、同じ写真から**1バイト違わない画像**を出す」
ところまで見ている。そこが合わないと「そろう」と言えないので。

## 7. 検証で見ること（作る前に決めておく）

この道具の決まりごととして、**足した検証は必ず1つずつ壊して、落ちることを確かめる。**

段階0

- 穴のあるフレームで、写真が**穴にぴったり**入っている（はみ出しも余りもしない）
- 穴の無いフレームでは、いままでどおり cover から始まる

段階1

- 焼きこんだPNGが、**ふつうの画像として開ける**（ここが壊れると全部だめになる）
- レシピの無いPNGを渡しても、いままでどおり動く
- **壊れたレシピ・知らない `v` を渡しても、行き止まりにならない**
  （読めなければ無視して、ふつうのフレームとして扱う）
- 固定した項目が、画面に**出ていない**（出ていて押せないのが、いちばん困る形）
- **同じフレーム・同じ写真から保存したものが、別の端末でも一致する**
  ← これが「そろう」の定義そのもの。ここを数えないと、そろったか分からない

段階2（作ることになったら）

- 初期表示で、フレームの画像を**1枚も取りにいっていない**
- 知らない `<id>` を開いても、行き止まりにならない
- 期限切れのリンクが、**期限切れだと分かる形**で閉じる

## 8. まだ決めていないこと

- 穴が円でないフレーム（縦長の窓、四角）をどこまで見るか
- レシピに作った人の名前を入れるか（入れるなら、それは掲載になる）
- 覚えておく機能（`src/lib/keep.ts`、いまは1枚だけ）を、配られたフレーム用に増やすか
- 段階2 に進むとき、上げた人をたどれる記録を残すか残さないか
  （残さないのも選択だが、開示を求められたときに「無い」と答えることになる）
